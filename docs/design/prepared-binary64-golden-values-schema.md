# Prepared binary64 golden payload · `spec:nrz:prepared-binary64-golden-values-schema`

This separately versioned CC0 payload supplies the independent endpoint evidence required by (`crit:nrz:transcendental-golden-acceptance`). It is not problem-data v2. The checker admits structure and exact arithmetic relationships; it neither executes a transcendental kernel nor proves the directed-rounding argument of an external implementation.

## Envelope and routes · `sec:nrz:golden-envelope-routes`

**Rule (Closed golden version)** · `rule:nrz:golden-version`

The envelope has namespace org.naturrhythmuszentrum.test.golden.prepared-binary64, version [1,0,0], owner NRZ, license CC0-1.0, sources and labels. Only that exact version is admitted. Sources are an ordered array of distinct repository-relative normal paths; labels are an ordered array of distinct labels. Array order is retained, not sorted by the checker. Object member order is immaterial to admission; duplicate members, missing members and unknown members are refused. Serialization puts the six envelope fields before routes and entries. Numbers carrying mathematical data are canonical reduced rational strings: an optional minus sign, a canonical unsigned decimal numerator, and an optional slash followed by a strictly positive canonical denominator. Integers omit the denominator; zero is spelled 0. Floats, leading zeroes, signed zero, unreduced fractions and denominator one are refused.

**Definition (Independent route registry)** · `def:nrz:golden-route-registry`

The payload routes array contains exactly two records, in this order: kind nrz-cas-enclosure, then kind mpmath-interval. Each record has id, kind, tool, revision, argument and exactly one precision field: precision_bits for CAS, precision_decimal_digits for mpmath. All text fields are nonempty, ids are distinct, and precision is a positive unsigned 64-bit integer. The argument records the route's directed-rounding justification and independence; it is provenance, not executable authority. Unknown kinds are refused; adding another route requires a new reviewed schema version. Each row's routes array names both ids in registry order, including expected-refusal rows, which carry no numerical evidence.

## Rows and evidence · `sec:nrz:golden-rows-evidence`

**Definition (Golden row)** · `def:nrz:golden-row`

Each entry has a unique nonempty id, operation, input, target, expected, routes and evidence. Operation is exactly exp, expm1, sigma, tanh or power. Input is either a point record with one rational point, or a box record with two ordered rational endpoints. Only power has an exponent, a canonical rational string. An enclosure row requires an exact dyadic exponent in (0,1]. An in-range non-dyadic exponent is admitted only with expected refusal non-dyadic-exponent; an exponent outside (0,1] is admitted only with expected refusal outside-domain. A dyadic in-range exponent cannot claim non-dyadic-exponent. Denominator classification uses exact budgeted arithmetic, including denominators beyond machine-word size; capacity excess remains an arithmetic resource failure. Exp and sigma use target kind absolute with unsigned bits; expm1 and tanh use relative with unsigned bits; power uses kind outward and no bits. A zero-bit target is representable. The target encoding ceiling is a resource bound, not a claim that binary64 can attain the target.

Expected is either the string enclosure or a record with exactly refusal, whose value is outside-domain, below-normal-operand, non-dyadic-exponent or target-not-certifiable. Enclosure rows additionally have golden. Refusal rows omit golden and have empty evidence, while still naming both registered routes. Non-dyadic-exponent is compatible only with power; outside-domain, below-normal-operand and target-not-certifiable are compatible with every operation, the last covering finite-schedule certification failure as well as width targets (`rule:nrz:transcendental-refusals`). Whether a given compatible refusal is the right runtime outcome remains outside admission. The law domains and signed below-normal rule remain those of the plan contract, not a second policy in this data decoder.

**Rule (Endpoint evidence association)** · `rule:nrz:golden-association`

For a point row, golden has exactly point, whose value is a rational interval pair. A box row instead has lower_endpoint and upper_endpoint pairs. Evidence is an array of endpoint records: one point record, or lower_endpoint then upper_endpoint. Each record has endpoint, input and routes; input repeats the original exact rational endpoint to bind the evidence to its argument. Its routes array has exactly two records in registry order, each with route (the referenced id) and interval (that route's ordered rational pair). Duplicates, missing or stray records, reversed record order and mismatched endpoint input bindings are refused. Relabelling all evidence and its inputs consistently cannot establish a transcendental truth; the provenance remains necessary.

**Rule (Exact intersection admission)** · `rule:nrz:golden-intersection`

For route intervals [l1,u1] and [l2,u2], the checker computes l=max(l1,l2) and u=min(u1,u2) using exact budgeted arithmetic. It requires l<=u, published golden=[l,u] exactly, and u-l<=2^(-120). No averaging or tolerance substitutes for equality. The ceiling applies separately to each endpoint golden, not to the full image of a box. Every promised elementary exact result is a singleton: exp(0)=1, expm1(0)=tanh(0)=0, sigma(0)=1/2, power at base 1 equals 1, and exponent 1 reproduces the base endpoint exactly. Other exact algebraic power values are not inferred by this structural checker. Relative-target consumers must still refine golden far enough to certify their endpoint error; a 120-bit absolute ceiling alone does not certify a relative error near zero.

## Resources and integration · `sec:nrz:golden-resources-integration`

**Rule (Bounded golden admission)** · `rule:nrz:golden-resources`

The public nrz_docgen::golden::read entry point takes a reader, explicit parsing Limits and a caller-owned CAS Budget, returning an immutable checked Payload. It reads fixed stack chunks and checks cumulative bytes before extending its owned input buffer; it does not trust file metadata or allocate the entire unbounded input first. Defaults are 1,048,576 input bytes, 256 entries, 4096 bytes per rational literal and 4096 target bits. JSON nesting has an explicit default and hard maximum of 64; a string-aware scan checks it before tree allocation, with a distinct Depth resource cause rather than a JSON syntax failure. An allocation-free schema-aware preflight then counts entries and decoded rational string bytes before the allocating JSON decoder starts. It recognizes escaped schema keys and accounts for UTF-8 and Unicode escapes, including surrogate pairs. Entries, Literal and Depth retain their distinct causes; no resource refusal becomes Json. Metadata and malformed unknown positions retain the aggregate byte ceiling, rather than acquiring a new unversioned per-string limit. A byte ceiling bounds the entire structural tree, metadata strings and evidence records; each row is then checked for its exact finite shape before rational work. CAS limits separately bound components, intermediates, formatting and cumulative arithmetic Work. Input-buffer reservation failure and byte excess have the byte-resource cause. The successful preflight retains no strings or collections. Serde scratch buffers, the admitted JSON tree, metadata maps and subsequent standard-library collections still use infallible allocation; a process-wide allocation failure there is not promised as a typed refusal. The bounded input and preflight constrain their size but do not provide fallible allocation throughout the decoder. No limit is a mathematical domain restriction.

The docgen data/check path reads authored JSON inputs under data/golden in filename order, refusing non-file or non-JSON entries. The check command performs this bounded admission before tracked-text reading and retains the existing ordinal checks afterward. It uses the default parsing ceilings and the measured per-entry CAS profile in (`tab:nrz:golden-fixture-costs`). The ordinary CAS defaults are Work=2,000,000 and literal_bytes=256; other CAS ceilings are unchanged. Each entry uses a fresh ledger. The aggregate ledger ceiling is the per-entry Work figure times the admitted entry count, computed by checked multiplication before arithmetic; size overflow retains the Work Capacity cause. The bounded entry count makes that product finite and independent of fixture size. There is no transferable spare allowance between entries. Parser literal capacity remains 4096 bytes; an otherwise structurally bounded input can still exceed the smaller local CAS literal capacity with its original typed arithmetic resource cause. No retry raises either ceiling. Test suites call the same validation logic; they do not implement another checker. The public caller-budget reader retains its cumulative caller policy, while authored-dataset admission supplies the per-entry ledgers. Arithmetic faults retain the engine's original typed cause, and the caller-owned ledger retains prior consumption on failure. Structural, encoding-resource and I/O errors remain distinct. Parsing does not claim CAS Work for ordinary JSON allocation or traversal.

**Criterion (Golden checker controls)** · `crit:nrz:golden-checker-controls`

The small fixture under tools/docgen/tests/support/prepared-binary64-golden-seven.json is a format sample. Its E1, M1, M0, sigma-ln-two-box, T0, P1 and R4 rows preserve the accepted sample's exact inputs and intervals. CAS 405d8d5 at 160 bits and mpmath 1.3.0 interval arithmetic at 150 decimal digits supplied the two routes; both original route intervals are retained. Controls mutate intersection operands, published intervals, route and endpoint association, closed kinds, canonical spelling, target forms, exact promises and width. Command-level coverage uses an oversized tracked golden and an ordinal sentinel to detect reversed admission order. Preflight controls assert that the allocating decoder was never entered for zero allowed entries, a 500,000-digit rational, 200,001 small entries and excessive nesting. Exact-limit and one-below controls cover byte, nesting, entry, literal, target and cumulative Work ceilings, including exact Limit/Work fault identity, permitted and needed values, and preserved prior consumption. **Criterion (Compact sigmoid and tanh golden coverage)** · `crit:nrz:golden-compact-sigmoid-tanh-values`

The sigma-* rows other than sigma-ln-two-box and the tanh-* rows spell represented binary64 operands exactly on [0,2] and [0,1], respectively. Each family covers zero, the upper endpoint and its normal predecessor, broad and narrow zero-containing boxes, the minimum normal endpoint and its successor, powers 2^(-40), 2^(-60) and 2^(-600), and the smallest and largest positive subnormal refusals. Each family also has an outside-domain refusal at the first binary64 value above its upper limit, and a 128-bit target refusal at its admitted upper endpoint. Exact comparison places the whole golden interval strictly between adjacent binary64 values, farther than 2^(-128) from either; this proves the spacing obstruction without a native evaluator. Both images are below one, so the absolute obstruction also implies tanh's relative obstruction. The underflow-scale input exposes a scale whose square underflows binary64; it asserts no native execution capability. The zero-to-minimum-normal box supplies endpoint evidence for later nominal-interior controls; the schema does not encode a nominal centre. The original rational sigma-ln-two-box remains mathematical reference evidence and is not a rounded native operand.

CAS f05491bdeb0466a02c8e65eaff92a723c0543fc8 supplies exact rational enclosures at 160 bits with the schedule retained in the route registry. (`[DOCGEN-test:integration:compact-golden-cas-route]`) recomputes each endpoint through the public enclosure API and replays the certificate in a fresh store. The separately directed route uses mpmath 1.3.0, revision b5c04506ef0cd4a1f1213f8389ee21c9c3551582, at 150 decimal digits. Its independent reproduction command is `PYTHONPATH=<mpmath-source> python3 tools/docgen/tests/support/sigmoid_tanh_intervals.py`, with that revision supplied as the source directory. It reads the authored inputs and compares only the retained directed intervals, never a CAS result. Sigmoid uses 1/(1+exp(-x)); tanh uses -m/(2+m) for m=expm1(-2*x). For 0<x<=1/1024, the alternating series has decreasing terms: the odd partial sum through degree 41 and the even sum through degree 40 enclose m, with every operation directed outward. This avoids cancellation at the smallest inputs. For larger inputs, directed exp(-2*x)-1 suffices. Outward dyadic coarsening retains the directed endpoints, with 128 fraction bits for sigmoid and 128+max(0,-floor(log2(x))) for tanh. Zero is evaluated exactly.

Both original route intervals are retained, and the published golden interval is their exact nonempty intersection. The CAS route has absolute precision; near zero it can be much wider than the directed route, so it alone does not establish relative golden precision. (`[DOCGEN-test:integration:compact-golden-associations]`) checks each nonzero tanh golden width against x*2^(-120), in addition to the unchanged absolute width check. Future native acceptance must contain the entire golden interval and satisfy its target; overlap is insufficient. Endpoint uncertainty, a box's image width and a native reading's numerical error are separate quantities. No negative-domain, derivative, reduction or saturation claim follows from these rows.
