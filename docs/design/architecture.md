# Conceptual architecture of the Naturrhythmuszentrum engine · `spec:vision:conceptual-architecture`

## Vision and principles · `sec:vision:vision-and-principles`

**Definition (Purpose and audience)** · `def:vision:purpose-and-audience`

Naturrhythmuszentrum is a matrix-based physics calculation engine for researchers, engineers, and developers who need numerical results whose dimensions, accuracy, and assumptions remain inspectable. It represents bodies, constraints, fields, and computational dependencies with petgraph, performs linear algebra through faer, and exposes physical quantities with dimensions, measures, and semantic kinds while keeping discrete counts distinct (`def:vision:dimensions`), (`def:vision:measures`), (`def:vision:counts`), (`rule:vision:semantic-kinds-and-roles`). Algebraic unit checks verify equations, blocks, and observables mechanically (`req:vision:algebraic-unit-checks`). Its central product is a result accompanied by evidence about its numerical reliability, conditional on a stated mathematical model and declared input uncertainty.

**Principle (Accuracy before speed)** · `prin:vision:accuracy-before-speed`

Accuracy determines whether a computation is acceptable; speed determines which acceptable implementation is preferable. This ordering prevents a fast result from concealing inadequate precision or an unsuitable algorithm. For example, a faster factorization loses to a slower solve when only the latter establishes the requested error budget, while equally adequate algorithms are compared by measured time and memory.

**Principle (Dimensions survive abstraction)** · `prin:vision:dimensions-survive-abstraction`

Dimensions, measures, semantic kinds, count domains and affine roles remain descriptor meaning through scalar arithmetic, matrix operations, solver interfaces and graph evaluation (`def:vision:dimensions`), (`def:vision:measures`), (`rule:vision:semantic-kinds-and-roles`). The bindings client checks original expressions and dynamic assemblies over the physics-free symbolic core at plan, binding and publication boundaries. Compile-time types enforce handle category, precision, evidence-owning validation state and roles fixed by engine code; they do not duplicate dimension algebra (`dec:nrz:descriptor-unit-authority`), (`def:nrz:checked-descriptor-boundary`). A solve still derives solution meanings from its right-hand side and operator, while a count cannot become a ratio merely because both have the zero dimension vector (`def:vision:counts`).

**Principle (Every physical value carries evidence)** · `prin:vision:values-carry-evidence`

Every public physical scalar and matrix carries an error companion because an isolated floating-point value cannot communicate its accuracy. Exact structural metadata, such as indices and permutations, is outside this requirement and is distinct from a physical count (`rule:vision:counts-and-metadata`). For example, importing measured values requires explicit uncertainty information or an explicit statement that only their represented numerical values are being modeled; absence of metadata never silently means physical exactness. An exactly declared count retains discrete exactness rather than acquiring an unrecorded floating-point approximation (`def:vision:counts`).

**Principle (Guarantees name their scope)** · `prin:vision:guarantees-name-scope`

Deterministic bounds, statistical uncertainty, numerical estimates, and modeling assumptions remain distinguishable because they support different conclusions. A certified solve bounds the solution of the declared mathematical problem over its declared admissible inputs; it does not certify the physical adequacy of that problem. For example, a small residual cannot erase uncertainty from an approximate constitutive law.

**Principle (Safety defines implementation boundaries)** · `prin:vision:safety-defines-boundaries`

Workspace code uses safe Rust and preserves the workspace-wide prohibition on unsafe code because performance cannot justify introducing unchecked memory obligations into engine code. Dependency integration uses safe public APIs. For example, matrix storage is designed around directly owned backend scalars instead of requiring an unsafe cast from slices of unit wrappers.

**Principle (Documentation is reproducible data)** · `prin:vision:documentation-is-reproducible`

Every repository Markdown document is a committed render of a minijinja template over hand-edited TOML inputs and derived JSON datasets because independently edited explanations and generated facts otherwise diverge. For example, changing a package dependency updates its derived documentation and committed render in the same meaningful commit.

**Principle (Boundaries remain independently reviewable)** · `prin:vision:reviewable-boundaries`

Packages, computational stages, and commits have explicit responsibilities because numerical trust depends on understanding where assumptions enter and where they are checked. For example, the matrix layer owns factorization certificates while the physics layer owns the decision that a particular constraint system represents a physical problem; neither silently supplies the other’s missing assumptions.

## Numerical model · `sec:vision:numerical-model`

**Decision (Precision selection)** · `dec:vision:precision-selection`

Precision is a scalar type parameter inside the numerical engine, initially supporting `f32` and `f64`, with `f64` as the default. Applications may select between complete typed computations through runtime dispatch at a problem boundary. This combines specialization of hot kernels with configurable execution without allowing a setting change to reinterpret existing storage. Extended precision is an admission path, not an initial capability: it requires compatible safe faer integration, validated arithmetic, and evidence that the additional accuracy justifies its cost. Exemplars: (`ex:exemplars:arb`), (`ex:exemplars:drake`).

**Table (Precision alternatives)** · `tab:vision:precision-alternatives`

|Alternative|Deciding criterion|Cost and disposition|
|-----------|------------------|--------------------|
|Type parameter throughout|Preserve specialized kernels and explicit conversion boundaries|Selected internally; increases compilation and potentially binary size through monomorphization.|
|Runtime scalar dispatch within arithmetic|Permit arbitrary precision changes inside one container|Rejected initially because dispatch, representation complexity, and backend compatibility would affect every operation.|
|Runtime selection of typed calculations|Configure a problem without obscuring its actual arithmetic|Selected externally; pays dispatch at coarse boundaries and requires explicit handling of differently typed outputs.|
|Arbitrary or extended precision immediately|Establish an accuracy need and a compatible backend|Deferred; storage, kernel support, and certification costs require measurement before admission.|

Exemplars: (`ex:exemplars:arb`), (`ex:exemplars:drake`).

**Rule (Precision conversions)** · `rule:vision:precision-conversions`

Precision conversion creates a new representation and updates its numerical envelope because rounding can change without changing a quantity’s dimension, measure, semantic kind, or point/difference role (`def:vision:dimensions`), (`def:vision:measures`), (`rule:vision:semantic-kinds-and-roles`). It is distinct from a measure conversion (`rule:vision:measure-conversions`). Widening preserves existing uncertainty; it cannot recover information already lost. Narrowing includes conversion error and rechecks applicable budgets. An authorized promotion policy may retry an entire operation or computation at higher precision, but records the attempt and returns an explicitly identified precision. Exemplars: none.

**Decision (Accuracy policy)** · `dec:vision:accuracy-policy`

A calculation policy selects assurance requirements, algorithms, refinement limits, and permitted precision escalation. Public operations default to requiring certified deterministic evidence for their declared admissible inputs; diagnostic estimates require explicit selection. Observable budgets use an absolute tolerance and a declared characteristic difference scale with the observable’s dimension and compatible kind, expressed in a common measure, and a dimensionless relative ratio (`def:vision:dimensions`), (`def:vision:measures`), (`rule:vision:semantic-kinds-and-roles`). The accepted bound is at most the absolute tolerance plus that ratio multiplied by the characteristic scale. A point’s tolerance is a difference: affine offsets never enter radii or relative scales (`rule:vision:measure-conversions`). Explicit scales prevent near-zero outputs, a changed unit, or a shifted coordinate origin from defining acceptance accidentally. Discrete count observables require an explicit count-error or ratio contract; a relative tolerance is never a count (`def:vision:counts`). Exemplars: (`ex:exemplars:higham-accuracy-and-stability`), (`ex:exemplars:sundials-and-differentialequations-jl`).

**Rule (Local and observable budgets)** · `rule:vision:local-and-observable-budgets`

An operation can track certified error without a local tolerance, but reports that no local budget was specified; it cannot report budget success in that case. Physics evaluations require budgets for requested observables because accuracy is otherwise undefined at the application boundary. Intermediate allocations are policy choices that may be revised during refinement, while the final observable budget remains authoritative. Exemplars: (`ex:exemplars:sundials-and-differentialequations-jl`).

**Decision (Factorizations and scaling)** · `dec:vision:factorizations-and-scaling`

The default square nonsingular solve uses pivoted LU, with partial pivoting as the initial candidate and explicit attention to growth and residuals. Rectangular least-squares problems use rank-revealing QR candidates, with SVD considered when rank separation or accuracy demands it. Cholesky is selected only for a supported symmetric positive-definite problem contract. Normal equations are excluded as the default least-squares route because they amplify conditioning difficulties. These are required adapter behaviors, not assertions about a particular faer release’s available APIs. Exemplars: (`ex:exemplars:higham-accuracy-and-stability`), (`ex:exemplars:kahan-and-wilkinson-matrices`).

**Rule (Equilibration)** · `rule:vision:equilibration`

Row and column equilibration uses recorded, invertible, dimensionless ratio transformations within an already compatible coordinate system because results and certificates must translate back to the declared problem (`def:vision:dimensions`), (`rule:vision:semantic-kinds-and-roles`). This numerical magnitude balancing is distinct from changing a measure and from physical nondimensionalization by typed reference scales (`rule:vision:measure-conversions`), (`rule:vision:heterogeneous-assembly`). Powers-of-two scaling is preferred where representable without damaging underflow because it can reduce additional rounding. Scaling never substitutes for conditioning analysis: improving the representation does not necessarily remove intrinsic sensitivity. Exemplars: (`ex:exemplars:higham-accuracy-and-stability`), (`ex:exemplars:kahan-and-wilkinson-matrices`).

**Decision (Reductions and residuals)** · `dec:vision:reductions-and-residuals`

Engine-controlled scalar reductions use compensated summation where its measured benefit warrants the cost; compensation improves accuracy but does not itself constitute a bound. Certified residuals and norms use an independently validated arithmetic path with conservative rounding treatment. This distinction allows faer to compute candidates efficiently while verification establishes what those candidates mean, without assuming an undocumented reduction order inside backend kernels. Exemplars: (`ex:exemplars:error-free-transformations`), (`ex:exemplars:extra-precise-iterative-refinement`).

**Decision (Refinement and mixed precision)** · `dec:vision:refinement-and-mixed-precision`

Iterative refinement is the first recovery mechanism after a useful factorization because correction solves can improve accuracy without repeating the most expensive work. A policy may factor in `f32` and evaluate residuals and corrections in `f64`, but accepts the result only after verification in the reported guarantee model. Refinement stops on success, stagnation, non-finite arithmetic, or an explicit iteration limit; failure triggers an authorized higher-precision retry or a numerical failure. Mixed precision is an optimization demonstrated by certificates and benchmarks, never an assumption that extra iterations restore missing digits. Exemplars: (`ex:exemplars:extra-precise-iterative-refinement`).

**Rule (Conditioning and refusal)** · `rule:vision:conditioning-and-refusal`

Condition estimates guide algorithm selection and explain sensitivity, but only validated bounds support certified conclusions. There is no universal condition-number cutoff because acceptable sensitivity depends on input uncertainty and the requested output budget. A computation refuses the requested guarantee when its perturbation margin cannot be established, its certified bound exceeds the budget, or its domain assumptions cannot be checked. An unsuccessful certificate means “cannot certify,” not “proved singular” or “proved inaccurate.” Exemplars: (`ex:exemplars:intlab`), (`ex:exemplars:hilbert-matrices`).

**Decision (Initial numerical domains)** · `dec:vision:initial-numerical-domains`

Initial production coverage is real dense arithmetic and supported real solve problems. Symmetric spectral problems follow once their structure and gap conditions can be validated. General spectra, complex results, and matrix functions require separately admitted domains because branch choices, defective eigenproblems, and singularities need guarantees beyond those of a solve. Unsupported requests return an explicit failure instead of projecting a complex result into real arithmetic or borrowing an unrelated certificate. Exemplars: none.

## Error-native, matrix-based error tracking · `sec:vision:error-native-matrix-tracking`

**Definition (Admissible values)** · `def:vision:admissible-values`

A scalar quantity consists of a represented center, its dimension, measure, semantic kind and point/difference role, an error companion, and provenance (`def:vision:dimensions`), (`def:vision:measures`), (`rule:vision:semantic-kinds-and-roles`). A homogeneous matrix consists of backend-native center storage, shape and structural metadata, an owner-level quantity descriptor, and the corresponding companion. Deterministic scalars use absolute difference bounds, vectors Euclidean bounds, and matrices Frobenius-radius perturbations, all expressed in the center’s difference measure. A point’s absolute radius carries no affine offset. Measurement and computational uncertainties are intrinsic contents, each with the descriptors of its own uncertainty expression; a relative bound, variance, covariance, or standard uncertainty must not inherit the center’s descriptor indiscriminately (`def:vision:intrinsic-uncertainty-companions`), (`rule:vision:uncertainty-unit-algebra`). Heterogeneous blocks need explicit normalization before one numerical norm or radius is meaningful (`rule:vision:heterogeneous-assembly`). Structural restrictions, such as symmetry, further restrict the admissible set when explicitly established. Discrete counts preserve their declared discrete value domain and exactness; a continuous expectation is a separate value kind, while a count’s standard uncertainty may be non-integer and has its own uncertainty kind (`def:vision:counts`), (`rule:vision:uncertainty-unit-algebra`). Exemplars: (`ex:exemplars:arb`).

Logical extent, axis meaning and structural evidence are specified by (`def:nrz:matrix-shape`), (`def:nrz:shape-structure`). The scalar normwise radius and optional componentwise array have different shapes and interpretations (`def:nrz:numerical-error-shapes`); heterogeneous restoration follows (`rule:nrz:shape-norms-and-conditioning`).

**Decision (Primary error model)** · `dec:vision:primary-error-model`

The primary model combines backward-error accounting for numerical algorithms with conservative forward envelopes for public values. Residuals establish how well a computed candidate satisfies its defining equation; verified sensitivity information converts that evidence into an enclosure of the requested result. Frobenius-radius envelopes are the initial representation because they compose with ordinary dense storage, have modest metadata cost, and bound the spectral norm where needed. Their conservatism is accepted initially and measured before introducing more expensive componentwise representations. The radius is carried within the matrix’s intrinsic companion together with the input and computational components it bounds; it does not replace separately declared probabilistic uncertainty or correlations (`def:vision:intrinsic-uncertainty-companions`), (`rule:vision:uncertainty-unit-algebra`). Exemplars: (`ex:exemplars:intlab`), (`ex:exemplars:arb`), (`ex:exemplars:higham-accuracy-and-stability`).

The shape model retains this choice and specifies optional componentwise forward and backward contracts without selecting their implementation (`def:nrz:numerical-error-shapes`). Neither a radius array nor a covariance is silently substituted for the scalar Frobenius envelope.

These sizes and tallies are algorithmic metadata, not physical counts (`rule:vision:counts-and-metadata`). Costs describe architectural expectations rather than measured performance. Exemplars: (`ex:exemplars:higham-accuracy-and-stability`), (`ex:exemplars:arb`), (`ex:exemplars:cadna-and-verificarlo`), (`ex:exemplars:measurements-jl`), (`ex:exemplars:interval-arithmetic-jl`).

**Decision (Roles of alternative models)** · `dec:vision:alternative-error-model-roles`

Forward enclosures are the public expression of the primary backward-error approach. Interval techniques provide the validated arithmetic substrate and independent small-problem test oracles; full interval matrices and affine tracking remain optional layers admitted only after demonstrating useful tightness for their cost. Affine uncertainty arithmetic tracks dependencies and is distinct from the affine measure coordinates of temperature points (`def:vision:measures`). Covariance propagation is an optional probabilistic layer with explicit source correlations. Stochastic arithmetic is a diagnostic and testing technique. Neither covariance nor stochastic variation is accepted as evidence that numerical roundoff lies within a deterministic budget, because neither promises that conclusion. Exemplars: (`ex:exemplars:interval-arithmetic-jl`), (`ex:exemplars:cadna-and-verificarlo`), (`ex:exemplars:measurements-jl`).

**Definition (Intrinsic uncertainty companions)** · `def:vision:intrinsic-uncertainty-companions`

A matrix contains its values and their uncertainty companions, related by declared logical entry and block maps rather than required to share one storage shape. Measurement uncertainty comes from inputs: deterministic enclosures, standard uncertainties, and declared correlations. Computational uncertainty comes from representation, arithmetic rounding, residual evaluation, and certificate construction. Both travel with every matrix operation as part of the resulting matrix’s contents; a later report is only a view of that carried evidence. Scalar quantities follow the same rule. The companion distinguishes source class, uncertainty expression kind, assurance, and provenance, because an input standard uncertainty and a certified computational radius support different conclusions.

Every uncertainty expression has its own dimension, measure, semantic kind, and point/difference role, derived from what it expresses about its values (`def:vision:dimensions`), (`def:vision:measures`), (`rule:vision:semantic-kinds-and-roles`). These need not equal the value’s descriptors. A relative uncertainty is a dimensionless ratio. A variance has twice its value’s dimension vector, and a covariance between values x and y has `D(x) + D(y)`. An affine point’s absolute uncertainty is a difference on its scale. An estimated discrete count can have a non-integer standard uncertainty: the standard-uncertainty kind is not a discrete count (`def:vision:counts`). A bound on a homogeneous operator block carries that block’s quotient dimension; a norm over a heterogeneous assembly needs an explicit normalized or otherwise dimensionally justified coordinate contract (`rule:vision:heterogeneous-assembly`).

The companion has its own logical extents and target identities as well as its own quantity descriptors (`def:nrz:companion-shape`). Full covariance pairs logical entries, including entries of a matrix value; it can therefore be larger than the value and cross homogeneous block boundaries (`def:nrz:covariance-shape`), (`conv:nrz:shape-entry-order`).

**Rule (Uncertainty unit algebra)** · `rule:vision:uncertainty-unit-algebra`

Algebraic unit checks cover uncertainty expressions and their propagation with the same rigor as value expressions (`req:vision:algebraic-unit-checks`). Each operation derives the output uncertainty descriptors from the input value descriptors and the chosen expression: an absolute radius or standard uncertainty has a compatible difference dimension, a relative radius or relative standard uncertainty is a ratio against a declared compatible nonzero scale, and covariance has the product of its two arguments’ difference dimensions and measures. Standard uncertainties and deterministic radii remain distinct semantic kinds even when their dimensions and numerical magnitudes coincide. Count uncertainty can be continuous without changing the discreteness of the underlying counted quantity, and an affine offset never becomes an uncertainty offset (`def:vision:intrinsic-uncertainty-companions`).

Conversions and normalization propagate every carried measurement and computational component together with its own measure and assurance. Absolute differences scale linearly, variances quadratically, cross-covariances by the two scale factors, and relative expressions according to their declared reference scales (`rule:vision:measure-conversions`). Shared-source identifiers and cross-correlations survive composition; absent covariance is not evidence of independence. A deterministic total combines only justified bound contributions and includes interaction terms; a standard uncertainty is not promoted to a worst-case radius. If a representation cannot preserve a requested uncertainty mode through an operation, that mode is explicitly unsupported. A matrix result cannot retain apparently valid uncertainty after its values or unit descriptors change; reports expose the intrinsic companion and do not repair missing propagation afterward.

Matrix propagation additionally checks paired axes, identities and sensitivity contractions under (`rule:nrz:shape-sensitivity-propagation`), (`rule:nrz:shape-data-time-evidence`). Relative references, undefined correlation and multivariate coverage have the separate contracts of (`rule:nrz:correlation-and-relative-shapes`), (`rule:nrz:expanded-uncertainty-shapes`). Structural compression must retain repeated-variable dependence (`rule:nrz:structured-companion-coordinates`).

**Definition (Error companion surface)** · `def:vision:error-companion-surface`

The intrinsic companion records the target mathematical meaning, measurement/input components, computational components, their uncertainty expression kinds and individual quantity descriptors, assurance, coverage assumptions, provenance identifiers, and a ledger of input, representation, arithmetic, and verification contributions (`def:vision:intrinsic-uncertainty-companions`), (`rule:vision:uncertainty-unit-algebra`). It includes a total deterministic difference radius only when relevant inputs are bounded and composition is justified. It separately retains declared standard uncertainties and correlations or covariance, and modeling or discretization claims. The owner carries these quantities with the values; their dimensions, measures, and kinds are derived individually, not copied wholesale from the center. Nonlinear interaction terms receive an explicit interaction entry instead of an invented attribution to independent causes. Exemplars: (`ex:exemplars:arb`), (`ex:exemplars:measurements-jl`), (`prob:exemplars:heat-conduction-one-dimensional`).

Each component also names its logical target map and independently derived shape (`def:nrz:companion-shape`), (`def:nrz:numerical-error-shapes`). The ledger distinguishes physical-input statistics from deterministic error in evaluating those statistics (`rule:nrz:shape-sensitivity-propagation`).

**Rule (Imports and exactness)** · `rule:vision:imports-and-exactness`

Constructors distinguish exact represented binary values, decimal values requiring conversion accounting, deterministic input enclosures, and probabilistic-only measurements because these describe different admissible inputs. Strict deterministic computation rejects missing required enclosures. Probabilistic-only values remain usable in explicitly selected uncertainty modes, with no claim that their physical values are deterministically enclosed. Constructors reject invalid radii and non-finite centers so later certificates do not inherit undefined arithmetic silently. Quantity imports also declare dimensions, measures, kinds, and affine roles; count imports check discreteness and keep structural metadata separate (`def:vision:dimensions`), (`def:vision:measures`), (`def:vision:counts`), (`rule:vision:semantic-kinds-and-roles`), (`rule:vision:counts-and-metadata`). Scale and offset conversions carry representation and arithmetic error without changing those declarations (`rule:vision:measure-conversions`). Exemplars: (`ex:exemplars:measurements-jl`), (`prob:exemplars:pendulum-gravity-estimate`).

**Rule (Arithmetic closure)** · `rule:vision:arithmetic-closure`

Arithmetic first checks dimensions, semantic kinds, and point/difference roles and converts compatible operands to a common measure (`req:vision:algebraic-unit-checks`), (`rule:vision:measure-conversions`). Addition then propagates both input radii and a validated bound on the discrepancy between the exact operation on represented centers and the stored candidate. Multiplication uses a bound of the form `norm(A) rB + rA norm(B) + rA rB + rounding`: every summand has the product dimension and compatible difference measure. These formulas include the perturbation interaction term because dropping it would turn a claimed enclosure into a first-order approximation. Each operation also propagates its supported measurement uncertainty and correlation mode, preserving separate descriptors and assurance for statistical and deterministic components (`def:vision:intrinsic-uncertainty-companions`), (`rule:vision:uncertainty-unit-algebra`). Transposition preserves a homogeneous matrix’s entry dimension and Frobenius radius; its domain and codomain follow the dual-space contract, while its entry permutation acts on every companion (`rule:nrz:shape-transpose-and-duality`), (`conv:nrz:shape-entry-order`). Extraction and reshaping use justified transformations rather than copying an unrelated certificate. Exemplars: (`ex:exemplars:arb`), (`ex:exemplars:higham-accuracy-and-stability`).

**Decision (Independent verification arithmetic)** · `dec:vision:independent-verification-arithmetic`

Certification does not depend on assuming a particular faer summation order. An independent safe arithmetic path encloses residuals and norms through validated endpoint operations, adjacent-representable-value adjustments where appropriate, and overflow-aware scaling. Its contract explicitly includes supported rounding behavior, subnormals, fused operations, and non-finite cases. This path can be substantially slower than a kernel; that cost is accepted for trustworthy initial guarantees and becomes a measured optimization target. Exemplars: (`ex:exemplars:fptaylor-and-gappa`), (`ex:exemplars:interval-arithmetic-jl`), (`cex:exemplars:rump-polynomial`).

**Definition (Certified solve contract)** · `def:vision:certified-solve-contract`

For a square center matrix `A`, center right-hand side `B`, and candidate `X`, let `rho` bound the Frobenius norm of the exact represented-center residual `B − A X`. Let `rA` and `rB` bound their input perturbations, `xnorm` bound the candidate’s Frobenius norm, and `g` be a validated upper bound on the spectral norm of the inverse of `A`. If `g rA < 1`, the output radius is bounded by `g (rho + rB + rA xnorm) / (1 − g rA)`, evaluated conservatively. The denominator expresses the admissible family’s distance from loss of invertibility, which is why the condition is part of the guarantee. For a homogeneous system, `D(X) = D(B) − D(A)`, `D(rho) = D(rB) = D(B)`, `D(rA) = D(A)`, `D(xnorm) = D(X)`, and `D(g) = −D(A)`, so `g rA` is a dimensionless ratio and the radius has `D(X)` (`def:vision:dimensions`), (`req:vision:algebraic-unit-checks`). Here `rA` and `rB` are absolute deterministic perturbation bounds on the operands, including their justified bounded measurement and prior computational contributions, not standard uncertainties or relative ratios. They and the computational residual/inverse-norm bounds are intrinsic companion quantities with individually derived measures and kinds (`def:vision:intrinsic-uncertainty-companions`), (`rule:vision:uncertainty-unit-algebra`). All terms use compatible canonical difference measures and kinds; point coordinates are first expressed relative to a declared origin. The returned solution owns its certified radius and carried uncertainty components; its report exposes that evidence. Propagating any declared standard uncertainties and correlations requires its separately supported statistical contract and cannot replace these deterministic hypotheses. Heterogeneous systems apply this theorem in recorded normalized coordinates and restore bounds per block (`rule:vision:heterogeneous-assembly`). Exemplars: (`ex:exemplars:intlab`), (`ex:exemplars:higham-accuracy-and-stability`).

The shapes and shared coordinate hypotheses for the residual, inverse witness, multiple right-hand sides and restored solution are specified by (`rule:nrz:shape-certified-solve`). This theorem bounds one declared deterministic perturbation family, even when the owner also carries a differently shaped statistical covariance.

**Decision (Initial inverse-norm certificate)** · `dec:vision:inverse-norm-certificate`

A baseline verifier may construct an approximate inverse `Z` and validate an upper bound `q` on the spectral norm of `I − Z A`, using a Frobenius upper bound where necessary. If `q < 1`, a conservative upper bound on `norm(Z) / (1 − q)` supplies the required inverse-norm bound. For a homogeneous operator, the approximate inverse has reciprocal dimension, so `Z A`, `I − Z A`, and `q` are dimensionless operators or ratios, never counts (`def:vision:dimensions`), (`def:vision:counts`), (`req:vision:algebraic-unit-checks`). Heterogeneous verification uses the normalized block coordinates of (`rule:vision:heterogeneous-assembly`). This method is chosen for its explicit, independently checkable theorem, not its scalability. Its cubic work and potentially loose Frobenius bounds make tighter verification methods a named early experiment. Exemplars: (`ex:exemplars:intlab`).

**Rule (Decomposition objects)** · `rule:vision:decomposition-objects`

Factorizations return opaque handles carrying permutations, transformations, reconstruction evidence, and applicable orthogonality or positivity evidence because those are relational claims about a decomposition. A reconstruction certificate does not imply small forward error in each factor. Exposing a factor as a general matrix therefore requires its own appropriate error companion and assurance status. The handle retains factor dimensions and compatible kinds and measures, or the normalization map when factorization uses dimensionless coordinates (`req:vision:powers-and-factor-dimensions`), (`rule:vision:heterogeneous-assembly`). Reusing a handle validates that the original center, precision, quantity descriptors, normalization, and relevant policy have not changed, preventing stale certificates. Exemplars: (`ex:exemplars:higham-accuracy-and-stability`), (`ex:exemplars:kahan-and-wilkinson-matrices`).

The handle checks intermediate axes and metric-dependent structure through (`rule:nrz:shape-factorizations`), including whether structure holds for the center or the whole admitted family (`def:nrz:shape-structure`). Shape and source identity are part of the evidence that reuse must preserve.

Factor reuse records the operator dependencies required by (`rule:nrz:computation-cache-validity`). A changed right-hand side requires its own residual, perturbation and budget evidence even when the operator factor remains valid, because factor evidence is not a point-specific solve certificate.

**Rule (Solves and explicit inverses)** · `rule:vision:solves-and-inverses`

Solving is the preferred interface because forming a complete inverse consumes storage and can produce unnecessary error when only its action is needed. An explicitly requested homogeneous inverse is treated as a matrix-valued solve against an exact dimensionless identity operator, has the reciprocal dimension, and receives a matrix envelope (`def:vision:dimensions`), (`req:vision:algebraic-unit-checks`). A heterogeneous inverse reverses the typed domain and codomain; identity zero blocks retain their required quotient dimensions, and numerical certification uses the recorded normalization (`rule:vision:heterogeneous-assembly`). Least-squares and rank-deficient operations need distinct rank and perturbation contracts; a square nonsingular solve certificate does not apply to them merely because a backend returns a candidate. Exemplars: (`ex:exemplars:higham-accuracy-and-stability`), (`ex:exemplars:intlab`).

Ordered inverse axes and the domain of several right-hand sides follow (`rule:nrz:shape-solves-and-inverses`). Their uncertainties retain the shared operator dependence under (`rule:nrz:shape-sensitivity-propagation`); independent per-column backward perturbations do not prove a common system perturbation (`def:nrz:numerical-error-shapes`).

**Rule (Spectral guarantees)** · `rule:vision:spectral-guarantees`

For supported symmetric admissible inputs, a normalized eigenpair residual can bound distance to some eigenvalue, but identifying a particular eigenvalue or bounding its eigenvector requires additional separation evidence. Repeated or clustered eigenvalues favor invariant-subspace guarantees because individual eigenvectors are not uniquely stable. General nonnormal eigenproblems remain separately gated because small residuals can coexist with large spectral sensitivity. Every spectral report identifies whether it bounds an eigenvalue set, an associated eigenpair, or a subspace. For `K v = lambda M v`, algebraic checks derive `D(lambda) = D(K) − D(M)`; mode-shape ratios and angular-frequency kinds remain distinct from counts and generic dimensionless scalars (`def:vision:dimensions`), (`rule:vision:semantic-kinds-and-roles`), (`req:vision:powers-and-factor-dimensions`). Exemplars: (`ex:exemplars:higham-accuracy-and-stability`), (`prob:exemplars:coupled-oscillators-normal-modes`).

Before applying these numerical results, the shape must admit one scalar eigenvalue dimension and the relevant self-adjoint identification or generalized pencil (`rule:nrz:shape-eigenproblems`). Square extents and numerical symmetry alone do not establish that physical domain.

**Rule (Matrix-function guarantees)** · `rule:vision:matrix-function-guarantees`

Each admitted matrix function supplies a domain check, an approximation-error bound, and a perturbation argument because function behavior depends on singularities and branch structure. Examples include separating a logarithm’s admissible spectrum from its excluded domain and bounding truncation in a supported exponential algorithm. A matrix exponential or logarithm requires a dimensionless endomorphism with a declared axis identification, possibly formed using a physical scale that gives the intended function its meaning (`rule:nrz:shape-powers-and-functions`). Arbitrary numerical nondimensionalization does not supply that physical contract; domain, codomain and semantic kind remain part of the check (`req:vision:algebraic-unit-checks`). A kernel returning a finite matrix is insufficient. Until these obligations are met, checked evaluation returns an unsupported-guarantee failure. Exemplars: (`ex:exemplars:arb`), (`ex:exemplars:higham-accuracy-and-stability`).

**Definition (Operation result and failure)** · `def:vision:operation-result-and-failure`

A numerical operation returns `Result<Outcome<T>, NumericalFailure>`. The outcome contains the value with its intrinsic uncertainty companion and a report exposing algorithm, precision, transformations, residuals, conditioning evidence, bound, budget status, and recovery attempts. The report does not substitute for uncertainties owned and propagated with the value (`def:vision:intrinsic-uncertainty-companions`). Category, precision, validation-state and fixed-role misuse fails at compile time. Descriptor dimensions, kinds, affine roles and block contracts are checked by the CAS before numerical evaluation and again at publication, with the offending expression, symbol, or block identified (`req:vision:algebraic-unit-checks`), (`req:vision:expression-and-symbol-contract`). Dynamic shape errors, unsupported guarantees, failed domain checks, non-finite arithmetic, and unmet budgets remain runtime failures. Ordinary numerical failure never uses a documented panic, because callers must be able to handle it as part of calculation. Exemplars: (`ex:exemplars:intlab`), (`ex:exemplars:hilbert-matrices`), (`cex:exemplars:rump-polynomial`).

A plan retains the operation outcome or refusal in (`def:nrz:operation-record`), with binding, point and node identities and the actual input versions. Batch collection preserves blocked and inactive nodes and point-local failures under (`rule:nrz:batch-outcomes`), because absence of an output must not be mistaken for numerical success or erase other points.

**Rule (Assurance and correlation)** · `rule:vision:assurance-and-correlation`

Certified and estimated access is distinguished for each uncertainty expression, and checked constructors control certified evidence because matching dimensions alone cannot promote a statistical estimate into a deterministic bound (`def:vision:intrinsic-uncertainty-companions`), (`rule:vision:uncertainty-unit-algebra`). The matrix owns both input/measurement and computational components and propagates them with every supported operation. Deterministic balls remain conservative without assuming input independence, although they can overcount shared error. Admitted covariance modes retain common-source identifiers and cross-covariances with product dimensions and difference measures; absent correlations are not silently replaced by independence. A refusal of deterministic certification does not erase separately valid probabilistic evidence. Reports reference the intrinsic companion and compact provenance instead of supplying a detached uncertainty record after evaluation. Exemplars: (`ex:exemplars:cadna-and-verificarlo`), (`ex:exemplars:measurements-jl`), (`prob:exemplars:pendulum-gravity-estimate`).

The same source may cross binding boundaries. Its joint relation remains available under (`rule:nrz:batch-source-covariance`), including cross-point blocks and explicit unknown correlations, because separate point records neither split a physical source nor justify independent aggregate errors.

## Units in the type system, as they meet matrices · `sec:vision:units-and-matrices`

The typed boundary enforces checked descriptor access; physical unit algebra remains descriptor data under (`dec:nrz:descriptor-unit-authority`).

**Definition (Dimensions)** · `def:vision:dimensions`

A dimension is an exponent vector over length, mass, time, electric current, thermodynamic temperature, amount of substance, and luminous intensity, in that fixed order. Their coherent SI base units are metre, kilogram, second, ampere, kelvin, mole, and candela. For a quantity expression `x`, write `D(x)` for its vector: `D(x y) = D(x) + D(y)`, `D(x / y) = D(x) − D(y)`, and `D(x^p) = p D(x)` for an admitted exponent `p`. The zero vector is dimensionless. A dimension contains neither a unit scale nor an affine origin, and does not distinguish every physical kind: counts, ratios, and angles all have the zero vector. Supported exponent representations and roots are constrained by (`req:vision:powers-and-factor-dimensions`).

**Definition (Measures)** · `def:vision:measures`

A measure specifies how a quantity of a declared dimension is expressed: its unit and scale relative to the coherent SI unit, together with an origin when the expression is an affine coordinate. With positive scale factor `s` and coherent-coordinate offset `o`, a point coordinate converts as `p_SI = s p_U + o`, while a difference converts as `delta_SI = s delta_U`. The factor is a dimensionless ratio; the offset is expressed in the target coherent coordinate. The measure is distinct from input uncertainty and from the semantic kind and point/difference role of the quantity. For example, a Celsius point uses scale one and offset 273.15 in kelvin coordinates, whereas a Celsius temperature difference uses scale one and no offset. A canonical kelvin coordinate can still represent a point; zero offset does not remove its role.

**Definition (Counts)** · `def:vision:counts`

A count is a discrete whole-number tally of a declared kind of thing, such as entities, complete cycles, events, or physical steps. Its SI dimension vector is zero, but its counted kind and discreteness are part of its contract. Counts are neither continuous dimensionless ratios such as strain and efficiency nor angles in radians, and they are not amount of substance: the mole has the amount-of-substance base dimension. An explicit physical relation, with its own dimension and kind checks, is needed to connect a count to an amount of substance. Count arithmetic preserves the counted kind and declared sign/range rules; a fractional quotient or statistical expectation is not silently returned as a discrete count. Numerical encoding must preserve declared exactness or account explicitly for representation loss.

**Rule (Semantic kinds and affine roles)** · `rule:vision:semantic-kinds-and-roles`

Every quantity has a semantic kind beside its dimension and measure because equality of exponent vectors proves only dimensional compatibility. Kinds distinguish at least discrete counted things, dimensionless ratios, and angles; the point/difference role additionally controls affine arithmetic. Addition, subtraction, comparison, and conversion require compatible kinds and roles as well as dimensions. Products, quotients, powers, and functions have declared kind rules instead of erasing kinds when exponents cancel. A same-kind count quotient can yield a ratio through an explicit operation; a rate of counted cycles and an angular frequency need an explicit cycle-to-angle relation even though both have inverse-time dimension. Neither an integer value nor the display string of a unit supplies this contract (`def:vision:dimensions`), (`def:vision:measures`), (`def:vision:counts`).

**Rule (Counts and structural metadata)** · `rule:vision:counts-and-metadata`

Matrix orders, indices, array extents, precision-bit selections, iteration limits, and configuration switches are structural or categorical metadata, not physical counts. A selector whose value happens to be an integer is not a ratio or a physical count. The input contract declares this role and validates the permitted category or range independently; it must not infer the role from a zero dimension vector, display text, or integer syntax. Metadata can control shape, repetition, indexing, or a declared exponent position, but enters physical arithmetic only through an explicit checked mapping. Physical counts retain the counted kind of (`def:vision:counts`), including when their representation is also an integer.

**Rule (Measure conversions and point arithmetic)** · `rule:vision:measure-conversions`

Conversion changes measure within a compatible dimension and semantic kind; it never changes a count into a ratio or an amount of substance (`def:vision:dimensions`), (`def:vision:measures`), (`def:vision:counts`), (`rule:vision:semantic-kinds-and-roles`). Conversion from measure U to V maps a point to `(s_U p_U + o_U − o_V) / s_V` and a difference to `s_U delta_U / s_V`. Conversion constants retain their exact mathematical definitions or declared enclosures; their numerical evaluation adds representation and arithmetic contributions to the companion. Difference radii scale by the absolute scale ratio and receive conversion-error bounds, never an affine offset; covariance scales by the corresponding products of scale ratios. Converting to a finer unit or wider precision cannot recover lost information.

Point minus compatible point yields a difference; point plus or minus compatible difference yields a point; differences support their declared linear arithmetic. Ordinary point plus point, multiplication, division, powers, or norms of points are rejected. An explicit affine combination with compatible points and dimensionless ratio weights summing to one is admissible, so a temperature midpoint need not pretend that ordinary point addition is valid. Linear solvers use differences from a declared origin and account for that translation in the right-hand side; they reconstruct points afterward. Where a physical law needs a multiplicative absolute temperature, it explicitly uses the difference from the distinguished absolute-zero origin. Conversion to canonical SI coordinates alone never authorizes forgetting the origin or role.

**Requirement (Algebraic unit checks)** · `req:vision:algebraic-unit-checks`

Every supported equation, assembled block, derived observable, and uncertainty expression must admit a mechanical unit check using (`def:vision:dimensions`), with measure compatibility and the semantic rules of (`rule:vision:semantic-kinds-and-roles`) and (`rule:vision:measure-conversions`). Addition and equality require equal normalized dimension vectors, compatible kinds and affine roles, and a common measure before combining coordinate numbers. Multiplication and division compose dimensions, admitted powers scale them, and both sides of an equation must agree. Zero entries retain their required descriptors; a numerical zero does not excuse a wrong block or equation dimension.

Dimensionless does not mean unrestricted: trigonometric functions consume declared angle arguments converted to radians, inverse trigonometric functions return angles from suitable ratios, and exponential and logarithmic arguments are dimensionless ratios in their admitted domains. Function signatures state dimension, kind, and role requirements. Compile-success and compile-failure checks exercise typed access boundaries, each rejection paired with a positive twin. Original expressions and heterogeneous blocks undergo CAS validation before assembly exposes normalized storage. An optional static comparison must agree with the CAS for its admitted subset and state its runtime checks and exclusions explicitly. The original-tree data-time checker supplies the reusable validation boundary (`rule:vision:check-before-normalization`). Production heterogeneous assembly and numerical conversion bounds remain obligations; problem schema v2 supplies generator validation (`spec:nrz:problem-data-schema`); the recorded descriptor/static experiment resolved representation without extending the numerical capabilities or proving legacy problem strings (`req:vision:expression-and-symbol-contract`), (`req:vision:unit-data-migration`).

**Requirement (Expression and symbol contract)** · `req:vision:expression-and-symbol-contract`

The physics-free `nrz-cas` core owns exact rational arithmetic, declaration keys, typed syntax, original occurrence trees and checked symbolic derivations. The bindings layer checks dimensions, measures, semantic kinds, counts and affine roles over those originals before requesting coordinate equalities. `source::parse_original` consumes an explicit semantic header from `Cas::context_header`; `Cas::walk_original` and `Cas::describe_syntax` retain every written operand and its byte span. Descriptor checking uses this single expression contract (`dec:nrz:descriptor-unit-authority`). Original syntax, proved equality, grammar and physical validation remain separate contracts (`def:vision:algebra-expression-trees`), (`dec:vision:algebra-normal-form`), (`conv:vision:algebra-text-syntax`), (`rule:vision:check-before-normalization`). Exact exponents remain subject to the bindings admission policy (`def:vision:dimensions`), (`req:vision:powers-and-factor-dimensions`).

Each quantity symbol, named dimensional constant, uncertainty symbol, and referenced observable needs an explicit declaration or checked derivation binding its dimension, measure, kind, and point/difference role. Metadata has separate declared uses (`rule:vision:counts-and-metadata`). A bare numeric coefficient is dimensionless; it cannot hide metres or seconds merely because a specialized example omitted them. Function meanings and symbol dependencies must be explicit, with unknown names and cycles in derived-observable definitions rejected. Coupled physical equations remain explicit systems rather than cyclic observable definitions (`dec:vision:physical-and-computational-graphs`). The bindings layer validates the original typed operations before algebraic rewrites can erase an invalid addition or affine operation, and preserves their contracts through normalization. Diagnostics identify the expression location and expected and derived descriptors. Dimensional consistency does not authorize numerically unsafe rewriting or establish an error bound (`req:vision:algebraic-unit-checks`).

Computational plans associate declared symbols with slots through (`def:nrz:plan-binding`), retaining original operations and declaration versions under (`rule:nrz:plan-validation`). Slot resolution belongs to the client, leaving the generic algebra core independent of storage and physical interpretation. The mathematical graph and proof boundary are specified by (`spec:nrz:cas-concept`); bindings and docgen use that boundary directly.

**Definition (Original expression occurrences)** · `def:vision:algebra-expression-trees`

CAS-owned original occurrences retain exact constants, declaration keys, ordered operations, rational exponents, named applications and source intervals. Shared syntax never merges distinct original uses. Clients complete original walks and validate physical operations before requesting an equality; substitution requires fresh traversal and physical checking. Exact coefficients use the CAS rational implementation with explicit resource ledgers. The bindings dimension contract additionally refuses components outside its signed numerator and unsigned denominator range. No floating value enters this exact arithmetic.

**Decision (Proved coordinate equality)** · `dec:vision:algebra-normal-form`

Bindings compares checked coherent coordinates by requesting `Task::Equal` from the CAS simplifier with an explicit target and domain contract. Successful outcomes contain replayed equality witnesses; conditional outcomes retain nonzero and other residual conditions. For example, `x - x = 0` is unconditional, while `x / x = 1` retains the nonzero condition on x. A refused or unfinished request supplies no equality. Original physical evidence remains attached to the checked expression independently of the coordinate theorem.

**Rule (Algebra domain boundary)** · `rule:vision:algebra-domain-boundary`

The CAS distinguishes equality on an admitted domain from equality of definedness sets through explicit domain contracts. Original operations and the witness retain domain obligations, including those beneath zero factors and cancellation. Bindings requests `DefinedAndEqual` for coherent-coordinate comparisons and does not promote physical nonzero declarations into mathematical assumptions. The core supports bounded checked symbolic derivations while remaining independent of physics, numerical evaluation and numerical certification (`spec:nrz:cas-concept`).

**Convention (Algebra text syntax)** · `conv:vision:algebra-text-syntax`

The bounded data-time grammar accepts ASCII identifiers, exact integer/decimal/scientific literals, explicit arithmetic, parentheses, rational literal powers and named applications. It preserves source operations and byte locations. Functions have no built-in physical meaning in the core. Implicit multiplication, unit suffixes, variable exponents, embedded equations, indexing and binders are unsupported; historical problem strings remain documentary; migrated executable fields use checked grammar or an explicit unsupported marker (`req:vision:unit-data-migration`).

**Decision (Data-time unit descriptors)** · `dec:vision:data-time-unit-descriptors`

The nrz-bindings data-time client uses seven exact rational SI exponents, an explicit semantic kind, an exact rational measure and a point or difference role. Runtime integral-only and rational exponent policies control descriptor admission; the selected typed boundary carries access evidence rather than a second exponent algebra (`dec:nrz:descriptor-unit-authority`). Measures require positive rational scales and rational offsets; symbolic or irrational scales return the named UnsupportedMeasureScale refusal. Multiplicative kind rules are registered explicitly and checked against dimension algebra. Compatible dimensions never infer kind identity. Count declarations carry whole-number domains, refuse unproved closure and use an explicit count_ratio relation; they do not become ratios or moles by sharing dimension exponents. Each uncertainty expression has its own radius, standard, relative, variance or covariance kind, dimension and measure; relative companions require a compatible declared nonzero difference reference. These descriptors implement the data-time vocabulary while numerical storage, conversion enclosures and propagation remain separate obligations (`rule:vision:uncertainty-unit-algebra`), (`req:vision:units-design-criteria`).

The matrix-scale extension preserves these scalar declarations while adding the indexed relationship and contraction evidence of (`rule:nrz:shape-data-time-evidence`). Correlation and expanded uncertainty are specified modes with separate implementation obligations, not capabilities inferred from the existing scalar registry (`rule:nrz:correlation-and-relative-shapes`), (`rule:nrz:expanded-uncertainty-shapes`).

**Rule (Check before normalization)** · `rule:vision:check-before-normalization`

The checker accepts original trees and explicit input, constant, metadata, derived-observable, uncertainty and function declarations. It visits all original operands before validating each operation; zero multiplication, cancellation and zero powers cannot hide invalid kinds or affine roles. Bare zero is a ratio; typed zeros need explicit declarations. Referenced definitions are expanded under resource limits with unknown-name and cycle diagnostics, and a whole-context check includes unused observables. Equations compare both sides and homogeneous blocks check each scalar entry before matrix storage is involved. Successful results retain original operations, node descriptors, exact conversion maps and declaration evidence, with separate optional proved-equality requests for coherent coordinates. Refusals identify operand paths, optional source byte spans, declaration chains, expected descriptors or operation constraints and derived descriptors. Trigonometric and inverse functions distinguish angle differences from ratios; other applications need declared signatures. A check establishes neither numerical domains nor an assurance claim, and a coordinate theorem cannot substitute for an original expression (`cav:vision:unit-checking-scope`), (`rule:vision:algebra-domain-boundary`).

Checking a flat list of scalar block entries does not establish a matrix map or covariance contraction. Ordered axes, typed zero positions, entry identities and structured maps require the additional checks of (`rule:nrz:shape-entry-contract`), (`rule:nrz:shape-data-time-evidence`).

Plan checks and concrete binding checks follow (`rule:nrz:plan-validation`), (`rule:nrz:binding-validation`). **Caveat (Scope of unit evidence)** · `cav:vision:unit-checking-scope`

An algebraic unit check proves consistency under declared dimensions, measures, kinds, and symbol meanings; it does not establish that those declarations describe the physical system, that an equation is the right law, or that its evaluation is accurate (`req:vision:algebraic-unit-checks`). Numerical enclosures, probabilistic assumptions, and model validity remain separate evidence. Collection equality is formal common-domain equality, not a numerical rewrite license or equality of definedness sets (`rule:vision:algebra-domain-boundary`). Declared source and assurance claims are retained without certification. A count with uncertain membership retains a discrete value domain; its standard uncertainty may be non-integer and has a distinct uncertainty kind (`rule:vision:uncertainty-unit-algebra`). A continuous mean, rate, or expectation requires its own value kind. The implementation must state unsupported kinds, exponents, affine operations, and data expressions instead of accepting them after metadata erasure.

**Decision (Homogeneous numerical leaves)** · `dec:vision:homogeneous-numerical-leaves`

Each dense numerical leaf has one composite dimension, canonical measure, and compatible semantic kind and linear role for its entire matrix because this maps directly to faer storage and makes matrix multiplication’s meaning uniform (`def:vision:dimensions`), (`def:vision:measures`), (`rule:vision:semantic-kinds-and-roles`). Heterogeneous systems are represented as typed homogeneous blocks with explicit domain and codomain structure. Affine point fields require the declared-origin treatment of (`rule:vision:measure-conversions`); a dense operator does not silently multiply points. Arbitrary per-element descriptors are excluded from the initial dense abstraction because they obstruct ordinary kernels and make addition and multiplication depend on element-level compatibility. Exemplars: (`ex:exemplars:uom-and-dimensioned`), (`ex:exemplars:nalgebra`), (`prob:exemplars:resistor-network`).

The logical axes, compatible partitions and structural constraints are defined by (`def:nrz:matrix-shape`), (`def:nrz:shape-structure`). The shape contract can distinguish repeated physical coordinates without requiring distinct wrappers on stored entries; homogeneous storage does not identify their values or uncertainty sources (`dec:nrz:shape-descriptor-ownership`).

**Rule (Heterogeneous assembly)** · `rule:vision:heterogeneous-assembly`

A block operator declares each variable block’s dimension `X_j` and equation block’s dimension `Y_i`, and verifies `D(A_ij) = Y_i − X_j`, including zero blocks (`def:vision:dimensions`), (`req:vision:algebraic-unit-checks`). Every product `A_ij x_j` must have the equation’s compatible kind and difference role, so terms in one row may be added after measure conversion. Block meanings are checked through descriptor and original-expression validation; types require the resulting checked binding before normalized storage is exposed (`def:nrz:checked-descriptor-boundary`). A physically heterogeneous vector has no single honest dimension, measure, or unnormalized Euclidean norm merely because it is concatenated (`def:vision:measures`), (`rule:vision:semantic-kinds-and-roles`).

After expressing points relative to declared origins, numerical nondimensionalization records positive typed reference scales `Sx_j` and `Sy_i` for variable and equation differences. It forms `xhat_j = x_j / Sx_j`, `bhat_i = b_i / Sy_i`, and `Ahat_ij = A_ij Sx_j / Sy_i`; algebraic checking proves their dimension vectors zero and retains the normalized-coordinate interpretation. The backend solves and certifies this recorded coordinate problem. Restoring each output block, its origin, and its error radius uses the same maps with conservative conversion accounting. Each operator block’s absolute uncertainty bound has its quotient dimension `Y_i − X_j`; each solution block’s absolute bound has `X_j`. A matrix-level norm bound has the descriptor of the declared normalized coordinate map, not a dimension inferred from concatenated storage. One normalized radius must not be reported as a common physical radius for metres and amperes. Measurement and computational companions propagate with the blocks, including relative ratios and covariance between differently dimensioned blocks, whose dimension is the sum of the paired vectors (`def:vision:intrinsic-uncertainty-companions`), (`rule:vision:uncertainty-unit-algebra`). Reference scales are physical quantities, distinct from measure scale factors and numerical equilibration (`rule:vision:measure-conversions`), (`rule:vision:equilibration`). Exemplars: (`prob:exemplars:spring-mass-truss`), (`prob:exemplars:resistor-network`).

The ordered operator contract, composition rules and recorded coordinate maps are specified by (`rule:nrz:shape-entry-contract`), (`rule:nrz:shape-composition`), (`def:nrz:shape-normalization`). Norm and condition-number claims name those coordinates or metrics (`rule:nrz:shape-norms-and-conditioning`); arbitrary normalization does not authorize a physical eigenproblem or matrix function (`rule:nrz:shape-eigenproblems`), (`rule:nrz:shape-powers-and-functions`).

**Decision (Storage and scalar wrapping)** · `dec:vision:storage-and-scalar-wrapping`

A scalar quantity combines a supported dimension-neutral interval or scalar with its companion and a quantity descriptor, attaching dimension, measure, semantic kind, and point/difference role at the quantity boundary (`def:vision:dimensions`), (`def:vision:measures`), (`rule:vision:semantic-kinds-and-roles`). The raw interval’s point constructor means an exactly represented singleton enclosure, not an affine physical point. Kernels receive safe normalized views only from validated bindings; category and precision markers prevent reference substitution, while mutable access updates or invalidates versioned evidence. **Requirement (Units design decision criteria)** · `req:vision:units-design-criteria`

Representation and typed-boundary choices follow soundness, expressiveness, inference, diagnostics, compilation cost and lint compatibility, in that order. The decision must preserve dimensions, measures, counts, semantic kinds and affine roles, with one authoritative original-expression checker (`def:vision:dimensions`), (`def:vision:measures`), (`def:vision:counts`), (`rule:vision:semantic-kinds-and-roles`), (`req:vision:expression-and-symbol-contract`). Equivalent cases compare exact equality, exponent admission, products, quotients, admitted roots, count refusals, multiplicative/affine conversions, independently dimensioned companions, ordered shapes and normalized computation. Compile-failure cases need positive twins, and diagnostics and timings are quoted only when observed.

The descriptor decision records an integral const-generic comparison compiled during the retired experiment and an argued assessment of richer type-level arithmetic and a closed table (`tab:nrz:descriptor-static-alternatives`). Its recorded smaller resistor fixture established the selected boundary without claiming full shape, factorization, conversion-enclosure or uncertainty support (`cav:nrz:descriptor-prototype-scope`). Those broader cases remain acceptance obligations of their implementing matrix and foundations bites, in that order. The separate schema lane implements problem data and generator validation under (`spec:nrz:problem-data-schema`), independently of the descriptor prototype decision. Exemplars: (`ex:exemplars:fsharp-units-of-measure`), (`ex:exemplars:uom-and-dimensioned`), (`ex:exemplars:nalgebra`).

**Rule (Canonical quantities and affine coordinates)** · `rule:vision:canonical-quantities-and-affine-coordinates`

Numerical quantity storage uses the declared coherent SI measure, with conversion error included in the companion, because equivalent measures must not alter physical meaning or hide representation loss (`def:vision:measures`), (`rule:vision:measure-conversions`). Source measure and origin remain available for reporting and conversion, and dimensions, semantic kinds, and point/difference roles survive normalization (`def:vision:dimensions`), (`rule:vision:semantic-kinds-and-roles`). Thus absolute temperature points and temperature differences retain different operations even in kelvin coordinates. Counts remain discrete, ratios remain continuous kinds, and angles remain angles despite their shared zero dimension vector (`def:vision:counts`). Descriptor authority and fixed role markers preserve these distinctions; numerical conversion kernels and their enclosures enter with matrix core bite 4, followed by quantity-facing conversions and discrete count storage in foundations bite 5 (`dec:nrz:descriptor-unit-authority`). Exemplars: (`ex:exemplars:mp-units`), (`prob:exemplars:heat-conduction-one-dimensional`).

**Requirement (Powers and factor dimensions)** · `req:vision:powers-and-factor-dimensions`

For an exact integer or rational exponent `p`, algebraic checking derives `p D(x)` and checks the operation’s semantic kind and role (`def:vision:dimensions`), (`rule:vision:semantic-kinds-and-roles`). The descriptor checker admits rational dimension exponents or selects an integral-only policy (`dec:vision:data-time-unit-descriptors`). The selected engine representation retains these runtime policies; the recorded integral const-generic comparison admitted a root only through a checked integral result witness and refused fractional lifts (`tab:nrz:descriptor-static-alternatives`). The generic algebra core’s rational expressions do not by themselves admit those results as physical quantity types (`req:vision:expression-and-symbol-contract`). Matrix adapters check reconstruction dimensions: homogeneous QR separates a dimensionless orthogonal operator from a factor carrying the original dimension; Cholesky factors require half that dimension. Internal numerical availability never justifies exposing an unsupported factor. Generalized squared frequencies use stiffness divided by mass; taking their square root still needs the declared angular-frequency kind. Heterogeneous factors retain the normalization and typed maps used by their handles (`rule:vision:heterogeneous-assembly`). Exemplars: (`ex:exemplars:mp-units`), (`prob:exemplars:coupled-oscillators-normal-modes`).

The admissible matrix powers, intermediate factor spaces, metric choices and common eigenvalue dimension are governed by (`rule:nrz:shape-powers-and-functions`), (`rule:nrz:shape-factorizations`), (`rule:nrz:shape-eigenproblems`). Scalar exponent admission alone establishes none of these matrix domains.

## Repository structure · `sec:vision:repository-structure`

**Definition (Baseline and proposed tree)** · `def:vision:baseline-and-proposed-tree`

The starting repository is a virtual nightly Cargo workspace with no members, a strict workspace lint configuration, an orchestration-linter snapshot assigning the root files and documents to one owner, and separate code and documentation/data licenses. The following packages are the target structure. Packages enter the workspace when they contain a coherent implemented responsibility, because empty scaffolding would create maintenance and documentation obligations without a usable boundary. Exemplars: none.

**Table (Packages and dependency direction)** · `tab:vision:package-structure`

|Directory and crate|Sole responsibility|Engine dependencies|
|-------------------|-------------------|-------------------|
|`crates/cas`, `nrz-cas`|Physics-free exact mathematical graphs, original occurrences and checked symbolic derivations|None of the other engine packages|
|`crates/scalar`, `nrz-scalar`|Supported scalar contracts, conversions, and validated primitive numerical operations|None of the other engine packages|
|`crates/accuracy`, `nrz-accuracy`|Dimension-neutral envelope primitives, assurance, policy, and compact provenance|`nrz-scalar`|
|`crates/bindings`, `nrz-bindings`|Authoritative quantity descriptors, exact measures, kinds and original-expression evidence; numerical integration follows|`nrz-cas`; later `nrz-scalar`, `nrz-accuracy`|
|`crates/matrix`, `nrz-matrix`|Matrix-owned scalar arenas and descriptor heaps, checked block views, faer adapters, and operation-specific certificates|`nrz-scalar`, `nrz-accuracy`, `nrz-bindings`|
|`crates/physics`, `nrz-physics`|Physical structures, constraint assembly, and computation plans and batch bindings using petgraph|`nrz-bindings`, `nrz-matrix`, `nrz-accuracy`|
|`crates/engine`, `nrz`|Curated application-facing exports and entry points|The public interfaces of the engine packages above|
|`tools/docgen`, `nrz-docgen`|TOML ingestion, deterministic datasets, minijinja rendering, and fixed-point verification|Tooling dependencies on `nrz-bindings` and `nrz-cas`|

Exemplars: (`ex:exemplars:faer`), (`ex:exemplars:herbie`), (`ex:exemplars:estate-tools-and-templated-documentation`).

**Rule (Layer enforcement)** · `rule:vision:layer-enforcement`

Dependencies flow downward through the declared package graph; scalar and accuracy primitives receive their dimensional and measure meaning from descriptor owners rather than depending back on bindings (`dec:vision:storage-and-scalar-wrapping`). The physics-free nrz-cas package depends on no other engine package. The data-time bindings client depends only on nrz-cas; numerical units integration may later add the declared scalar and accuracy edges. The descriptor experiment is retired; its recorded decision assigns production responsibilities to existing owners (`dec:nrz:descriptor-prototype-promotion`). Scalar primitives remain independent of algebra and bindings. The expression boundary is specified by (`req:vision:expression-and-symbol-contract`). A metadata-based architecture check compares normal, build, development, and feature-dependent edges against the permitted graph because a forbidden dependency remains a coupling even when hidden in tests. Cross-layer integration tests live at an existing upper layer. The facade reexports supported concepts and adds no competing numerical implementation. Exemplars: none.

**Rule (Backend boundaries)** · `rule:vision:backend-boundaries`

Only the matrix package integrates faer. Physics owns physical and computational petgraph schemas, while `nrz-cas` owns its private mathematical graph; neither graph representation becomes a numerical or physical descriptor API. Backend matrices are borrowed or owned behind engine interfaces that check and preserve dimensions, canonical measures, kinds, affine roles, and any block normalization maps (`req:vision:algebraic-unit-checks`), (`rule:vision:heterogeneous-assembly`). Public escape hatches clearly return raw centers and consume or detach guarantees where necessary, preventing external mutation from leaving apparently valid evidence attached. Exemplars: (`ex:exemplars:faer`).

Adapters also preserve logical axes, structure scope and entry maps independently of backend layout (`def:nrz:matrix-shape`), (`def:nrz:shape-structure`), (`conv:nrz:shape-entry-order`). An adapter's numerical shape check cannot replace these physical and companion checks.

The matrix owner resolves public descriptor handles and validates safe views before entering faer (`dec:nrz:heap-ownership-and-sharing`), (`rule:nrz:descriptor-layout-validation`). Physics plans use that public boundary; bindings remains a checker and algebra remains generic, because storage ownership must not introduce a reverse dependency.

**Decision (Physical and computational graphs)** · `dec:vision:physical-and-computational-graphs`

Physical relationships and computation dependencies use distinct graph schemas because a physical cycle is not automatically a scheduling error. Acyclic dependencies can be scheduled directly; coupled constraints are assembled into explicit systems or declared iterative procedures. Cache validity includes input identity, precision, dimension, measure and origin, semantic kind and role, block scales, expression/symbol declarations, policy, and evidence dependencies because reusing a center under changed assumptions would invalidate its companion (`def:vision:dimensions`), (`def:vision:measures`), (`rule:vision:semantic-kinds-and-roles`), (`req:vision:expression-and-symbol-contract`). Discretization and modeling errors remain separate ledger entries with their own coverage. Exemplars: (`ex:exemplars:drake`), (`ex:exemplars:modelica`).

The computational representation is (`def:nrz:computation-plan`), with immutable operation contracts and separate bindings. Admitted families of bindings follow (`def:nrz:computation-batch`), (`rule:nrz:batch-variation`); their checks, records, cache dependencies and replay order follow (`rule:nrz:plan-validation`), (`rule:nrz:binding-validation`), (`def:nrz:operation-record`), (`rule:nrz:computation-cache-validity`), (`conv:nrz:batch-order-and-replay`). This makes data variation explicit while preserving the distinction between a physical cycle and a computation dependency.

**Rule (Tests, examples, and worked problems)** · `rule:vision:verification-locations`

Package-local tests exercise the package contract; integration tests live under that package’s `tests/` directory when they cross its public interface. Bindings tests exercise dimensions, measures, counts, semantic kinds and affine roles through CAS acceptance/refusal tests. Compile-failure and compile-success twins exercise category, precision, validation state, physical/normalized views and fixed roles; the optional exponent probe separately checks its static dimension guarantee because rejection is an observable feature (`req:vision:algebraic-unit-checks`). Generator tests validate declared data expressions and their symbol dependencies; assembly tests reject incompatible dynamic blocks before backend calls. Cross-route cases check agreement of static and data-time dimension normalization, while conversion cases check point and difference bounds (`req:vision:expression-and-symbol-contract`), (`rule:vision:measure-conversions`). Matrix fixtures live under `crates/matrix/tests/fixtures/`, while executable examples and benchmarks live in the relevant package’s `examples/` and `benches/` directories. Cross-layer worked problems live under `data/problems/`, each with an identified physical model, inputs, expected observables, and generated explanatory documentation, so validation connects numerical results to a stated problem. Exemplars: (`prob:exemplars:spring-mass-truss`), (`prob:exemplars:resistor-network`).

**Rule (Independent numerical evidence)** · `rule:vision:independent-numerical-evidence`

Tests combine small exact or independently bounded references, adversarial conditioning cases, structural identities, and whole worked problems because no single oracle covers both arithmetic correctness and model assembly. Higher precision is useful reference evidence but is not automatically truth. Fixtures include scale imbalance, cancellation, near-singularity, repeated spectra, correlated inputs, and budget boundaries. Benchmark reports pair speed with achieved assurance and accuracy; a faster failing computation is not recorded as an improvement. Exemplars: (`ex:exemplars:herbie`), (`ex:exemplars:interval-arithmetic-jl`), (`ex:exemplars:hilbert-matrices`), (`ex:exemplars:kahan-and-wilkinson-matrices`), (`cex:exemplars:rump-polynomial`).

**Decision (Documentation layout)** · `dec:vision:documentation-layout`

Each Markdown render has its minijinja template at `templates/{output}.j2`, mirroring the output path. Hand-edited TOML inputs live under `data/inputs/` and `data/problems/`, and generated JSON datasets live under `data/datasets/`. Root, documentation and package renders remain in their reader-facing locations. This arrangement keeps the source of an explanation discoverable without requiring all documentation to move away from the code it explains. Exemplars: (`ex:exemplars:estate-tools-and-templated-documentation`).

**Rule (Documentation envelope and derivation)** · `rule:vision:documentation-envelope-and-derivation`

Each input envelope identifies its document or dataset, labels, ownership reference, license classification, and source relationships because rendering must preserve estate metadata as well as prose. Exact keys follow the orchestration linter’s actual schema once available. Derived JSON is reproducible from committed inputs, metadata, and fixtures; live clocks, network responses, unordered traversal, and live benchmark timing are excluded because they would prevent reproducible renders. Recorded measurements include their environment and provenance before entering documentation. Exemplars: (`ex:exemplars:estate-tools-and-templated-documentation`).

**Rule (Fixed-point gate and bootstrap)** · `rule:vision:fixed-point-gate-and-bootstrap`

The documentation gate regenerates datasets and renders in an isolated output area, compares bytes and output inventory with the committed state, and verifies that another generation produces no change. This detects drift, stale outputs, and self-feeding transformations. The generator’s first usable commit includes its own documentation inputs, templates, and renders, together with the converted architecture document; the bootstrap therefore establishes the same rule that subsequent commits must obey. Exemplars: (`ex:exemplars:estate-tools-and-templated-documentation`).

**Decision (Labels and ownership)** · `dec:vision:labels-and-ownership`

Root policy remains with the declared root owner until an explicit partition update is committed. The proposed partition assigns each package subtree and each cross-cutting documentation or worked-problem subtree exactly one declared owner responsibility, with an actual estate owner resolved through the linter configuration. Ownership of templates, inputs, datasets, and renders follows their subtree responsibility. Labels remain stable across moves and use unique semantic identifiers because citations should survive changes in file layout. Exemplars: (`ex:exemplars:estate-tools-and-templated-documentation`).

**Rule (Metadata and licenses)** · `rule:vision:metadata-and-licenses`

Every document and source carries the required labels and passes the orchestration linter because ownership and traceability apply to generated and handwritten material alike. Program code is AGPL-3.0-only; data and documentation are CC0-1.0. Generator logic, narrative content, fixtures, and outputs receive explicit classifications so a generated file does not accidentally inherit a tooling file’s metadata. Third-party material retains its applicable attribution and is not relabeled by generation. Exemplars: (`ex:exemplars:estate-tools-and-templated-documentation`).

**Rule (Gate of record)** · `rule:vision:gate-of-record`

A green commit passes the pinned nightly formatter, the declared rustc and clippy posture, documentation checks, appropriate unit and integration tests, compile-time boundary acceptance and rejection with positive twins, implemented data-time algebraic checks and assembly-time block checks, orchestration linting, architecture checks, and documentation fixed-point verification (`req:vision:algebraic-unit-checks`). Relevant supported feature configurations are checked because inactive features can otherwise hide violations. Unsafe code remains forbidden; missing documentation, missing Debug implementations, unreachable public items, unwrap, unfinished placeholders, debugging macros, and print macros remain denied as specified. Routine tooling output uses an appropriate fallible I/O interface instead of weakening these rules. Exemplars: (`ex:exemplars:estate-tools-and-templated-documentation`).

**Rule (Meaningful commit series)** · `rule:vision:meaningful-commit-series`

Each main-branch commit is one independently reviewable, green unit with a Conventional Commits subject and a body explaining why. A typical bite first establishes a usable contract and its rendered documentation, then adds a minimal supported implementation with its meaningful tests, then adds separately justified capabilities or optimizations. Tests accompany the behavior they validate; generated artifacts accompany the source change that causes them. An indivisible cross-package contract change stays together because artificial splitting would leave intermediate commits incoherent. Exemplars: none.

## Risks and open questions · `sec:vision:risks-and-open-questions`

**Caveat (Backend capability uncertainty)** · `cav:vision:backend-capability-uncertainty`

No particular faer version, decomposition API, threading behavior, or extended-scalar capability is established here. The numerical feasibility bite audits a selected version’s safe interfaces and exercises the required candidate operations. Acceptance requires safe integration and correct residual verification; an unavailable advanced operation remains unsupported until a compatible implementation path exists.

**Caveat (Validated arithmetic assumptions)** · `cav:vision:validated-arithmetic-assumptions`

Certified envelopes depend on correctly handling primitive rounding, subnormals, overflow, and norms. The feasibility bite tests a small validated arithmetic implementation against exact small-case references and targeted floating-point boundaries on supported environments. Failure narrows the supported platform contract or blocks certification; it does not downgrade a guarantee invisibly.

**Caveat (Certificate cost and looseness)** · `cav:vision:certificate-cost-and-looseness`

Frobenius envelopes and approximate-inverse verification can be too conservative or expensive for large systems. The first matrix bite measures accepted-budget rates, certificate width, runtime, and memory over scaled and ill-conditioned problems. Componentwise bounds, tighter inverse-norm verification, or structured uncertainty become candidates only if they materially improve these measurements while preserving a checkable argument.

**Caveat (Transitive unsafe code)** · `cav:vision:transitive-unsafe-code`

Workspace-wide prohibition establishes a rule for workspace-authored code; it does not establish that third-party implementation internals contain no unsafe code. The feasibility audit records the dependency trust boundary and verifies that engine integration needs only safe APIs. A requirement to exclude unsafe transitively would need separate examination against the fixed faer backend and could require an explicit constraint amendment rather than an unsupported assurance.

**Caveat (Lint feasibility)** · `cav:vision:lint-feasibility`

The declared lint posture is stricter than ordinary numerical projects and may expose conflicts in tests, generated interfaces, or primitive arithmetic. The generator and feasibility bites compile minimal representative implementations under the actual configuration. Any genuine incompatibility is reported with the smallest necessary argued change; this architecture grants no blanket allowances or exemption for test code.

**Open Question (Dimension encoding and semantic kinds)** · `open:vision:dimension-encoding-and-semantic-kinds`

The representation question is resolved by (`dec:nrz:descriptor-unit-authority`): exact descriptor data and original-expression CAS checks remain authoritative, with category, precision, validation-state and fixed-role types at computation boundaries. The recorded seven-const comparison added unequal-dimension addition rejection but still needed semantic checks and explicit result annotations; fuller type-level arithmetic and a generated table are not selected as engine authority (`tab:nrz:descriptor-static-alternatives`). Counts, ratios, angles and metadata remain obligatorily distinct (`def:vision:counts`), (`rule:vision:counts-and-metadata`). Remaining work is promotion by the production owners and numerical evidence; the separate schema lane implements reference-data validation (`dec:nrz:descriptor-prototype-promotion`), (`req:vision:unit-data-migration`).

**Caveat (Correlated and nonlinear uncertainty)** · `cav:vision:correlated-and-nonlinear-uncertainty`

Covariance linearization can understate uncertainty near nonlinear transitions, and deterministic balls can greatly overstate it when dependencies repeat. The uncertainty extension compares shared-source examples, affine or interval references, and sampling diagnostics without treating sampling as proof. Admission requires a visible validity domain and useful improvement over the primary companion.

**Caveat (Spectral and function coverage)** · `cav:vision:spectral-and-function-coverage`

Repeated eigenvalues, nonnormality, rank changes, and function-domain boundaries defeat generic error recipes. A separate advanced matrix stage begins with symmetric spectral examples and explicit separation tests, then evaluates each additional operation against an operation-specific oracle. Failure to establish a domain or certificate keeps that capability outside checked evaluation.

**Open Question (Physical model coverage)** · `open:vision:physical-model-coverage`

The first representative bodies, fields, constraints, and integration procedures are not specified. The physics-design portion selects worked problems that exercise homogeneous and heterogeneous assembly, coupled constraints, and measurable numerical sensitivity. Each problem states whether discretization and modeling error are bounded, estimated, or outside its guarantee, so numerical certification cannot be mistaken for complete physical validation.

**Caveat (Estate schema and reproducibility)** · `cav:vision:estate-schema-and-reproducibility`

Exact envelope fields, source-label placement, and additional owner identities are unavailable at this architectural boundary. The documentation generator bite resolves them against the declared linter snapshot and proves the output fixed point. Numerical reproducibility is evaluated separately across execution settings: deterministic documentation is mandatory, while numerical reports must identify settings that can affect centers, certificates, and diagnostic experiments.

## Mapping onto the plan · `sec:vision:mapping-onto-the-plan`

**Decision (Sequencing adjustment)** · `dec:vision:sequencing-adjustment`

Documentation generation remains first because every later architectural decision needs a reproducible repository representation. A numerical feasibility stage follows before the units design is finalized, because scalar contracts, certification costs, and backend boundaries constrain a useful bindings interface. Units design selects descriptor authority and typed checked access using the generic expression/symbol contract and a static comparison; the schema migration lane implements the existing data obligation, while the algebra core remains physics-free (`req:vision:expression-and-symbol-contract`). Certified matrix core is bite 4 and precedes units and numerical foundations at bite 5: matrix-owned value and companion regions, production element arithmetic, floating conversion kernels and matrix-level propagation supply the foundation for the quantity-facing surface. CAS work remains descriptor and symbolic work; heap numbers remain in floating kernels. The two semantic step labels are retained. Advanced numerical domains remain separate because every decomposition or matrix function needs its own proof.

**Table (Bites and architectural obligations)** · `tab:vision:bite-mapping`

|Sequence|Relationship to the original plan|Architectural work and completion evidence|
|--------|---------------------------------|------------------------------------------|
|1. Documentation generator|Original bite 1|Establish `tools/docgen`, `nrz-docgen`, envelope handling, deterministic datasets, mirrored sources under `templates/`, ownership integration, and fixed-point checks; import this architecture as a committed render.|
|2. Numerical feasibility|Added prerequisite|Validate scalar and arithmetic contracts, safe faer integration, representative lint compatibility, and baseline residual/inverse-norm certification; record measured limitations before committing to broad APIs.|
|3. Units design|Original bite 2|Decide descriptor representation and typed evidence boundaries; compare the integral static probe and assess rejected alternatives; identify the independently implemented problem schema and generator checks (`req:vision:units-design-criteria`).|
|4. Certified matrix core|First part of original bite 4, moved before quantity integration|Implement the matrix-owned heap, arenas, category/precision handles, checked layouts/views, value versions, atomic value/companion publication, element rounding, floating conversion kernels, matrix-level deterministic/covariance/numerical-error propagation and the certified square solve; verify independent bounds, source cross blocks, normalization, budgets and invalidation (`rule:vision:heterogeneous-assembly`), (`rule:nrz:shape-certified-solve`).|
|5. Units and numerical foundations|Original bite 3 surface, now built on the heap|Expose descriptor-backed quantities as heap regions, exact discrete counts, points/differences, measure/precision conversion through checked kernels and data-time binding; verify typed access, count domains, conversion bounds and original-expression evidence (`req:vision:algebraic-unit-checks`), (`req:vision:unit-data-migration`).|
|6. The same bites implement the computation contracts: units design settles descriptor authority; matrix core bite 4 implements reusable schema/binding checks, safe heaps, companion propagation and operation records; foundations bite 5 exposes quantities and data-time integration over them; physics owns plans and admitted binding families; advanced domains extend their own contracts; consolidation checks joint-source batches and replay (`dec:nrz:computation-model-implementation-boundary`). No extra bite or numerical capability is implied by this design.

**Rule (Verification is continuous)** · `rule:vision:verification-is-continuous`

Accuracy testing and representative measurements accompany every numerical bite because the final benchmark stage cannot repair an architecture built on untested guarantee assumptions. The consolidation stage broadens coverage and compares alternatives; it is not the first point at which accuracy is examined. Algorithm changes regenerate affected reports and fixtures in the same meaningful commit when their recorded conclusions change.

**Rule (Completion boundaries)** · `rule:vision:completion-boundaries`

Each bite declares its supported domain, assurance level, error behavior, and outstanding exclusions in generated documentation because completion must be reviewable without assuming future work. A bite that cannot establish its intended guarantee either narrows its explicitly supported domain or remains incomplete. The engine’s growth is therefore measured by verified capabilities and usable physical problems, rather than by the number of backend operations exposed.
