# Versioned problem data · `spec:nrz:problem-data-schema`

This specification implements the contract of (`req:vision:unit-data-migration`). The schema and generator migration is owned by NRZ and the units/docgen maintainers. Numerical quantities, conservative conversions, intrinsic numerical companions and matrix contracts remain foundations work. This document is introduced before the generator and input switch: until that atomic switch, v1 inputs still receive shape validation only.

## Source records · `sec:nrz:problem-data-records`

**Rule (Problem data versions)** · `rule:nrz:problem-data-versions`

Use version = [2, 0, 0] in both problem/fixture envelopes and the derived problems dataset. Keep the existing problem and fixture namespaces. Keep unrelated document, project and census envelopes at their existing versions. Accept 2.0 patch revisions only when they retain the same field and semantic contract; reject unknown minor or major versions with a supported-version diagnostic. Shape axes, indexed companions, versioned shared sources and batch axes require an explicitly admitted later schema version, not ignored extra keys. All structured records deny unknown fields, and every symbol namespace and tagged alternative has an exact key set.

**Definition (Problem data records)** · `def:nrz:problem-data-records`

The six envelope fields remain namespace, version, owner, license, sources and labels. Their current meanings, order, owner NRZ, CC0 license, empty source arrays and one existing register label are preserved for each input. The dataset retains its ordered source paths and empty labels. No label, parameter, observable, variant or existing source identity is renamed.

The payload has these fields:

- problem: the existing slug, title, register, kind, model and instance strings. Location/slug/kind/register checks remain. Model and instance remain preserved documentary text.
- exponent_policy: integral or rational, mapped directly to ExponentPolicy. The migrated inputs use rational, with explicit rules admitting the roots they need; integral-policy refusal is covered by synthetic tests.
- kinds: an ordered list of explicitly declared kind records. Each record has name, type and dimensions, where dimensions is seven exact rational strings in length, mass, time, current, temperature, amount, luminous-intensity order. Ratio and angle require zero dimensions. Named kinds use the supplied stable name and dimension. Count kinds additionally require thing and domain; domain has optional inclusive minimum and maximum integer bounds, and neither bound means signed integers. Uncertainty kinds additionally require mode, value_kind and, exactly for covariance, other_kind. Their dimensions must equal the checker's derived dimensions. Kind references are unique, bounded and acyclic. Kind equality is never inferred from equal dimensions.
- kind_rules: an ordered list of tagged multiply/divide records with left, right and result kind names, or power records with base, exponent and result. The exponent is an exact signed integer or rational. Every record also has reason, describing the physical interpretation being declared. Register each rule with Registry::register_binary or register_power; reject duplicates, invalid dimensions, unavailable kinds and forbidden count rules. Do not synthesize rules by looking for matching dimensions. Intermediate kinds needed by products, squares, reciprocals and roots are declared explicitly in kinds.
- parameters: the source-ordered parameter records described below; all 73 existing names, descriptions and value strings stay intact.
- symbols: an optional source-ordered list of additional constants and derived helper declarations, default empty. Common fields are name, description, descriptor, source and assurance. An exact-constant alternative additionally requires value; a derived alternative requires expression. No arbitrary untyped symbolic constant is admitted. Helpers are distinct from original parameters and observables and may not collide with their names.
- observables: the source-ordered result records described below; all 90 existing names and expected values remain.
- equations: an optional list, default empty, of name, left, right, source and assurance records. Left and right are algebra expressions with their own source locations and are checked with check_equation. This does not solve an equation or prove that the equality holds numerically. An unsupported equation instead carries the same explicit unsupported alternative as an observable expression.
- variants: the existing name, description, overrides and expected fields, with the same strings and mappings. Overrides continue to replace parameter value strings only. No variant can change a role, descriptor, count domain or metadata category. Expected remains documentary reference text, not an executable expression or a numerical result claimed by docgen.
- errors: the existing bounded, estimated and excluded string arrays, unchanged.
- stress: the existing claims and bites label arrays, unchanged.

A descriptor record has dimensions, kind, measure and affine_role. Dimensions contains all seven exact rational exponents and must match the named kind's independently constructed Dimension. Kind names one declared kind. Measure requires display, scale and offset; scale and offset are exact numeric strings, display is reporting text, scale is strictly positive, and no scale or origin is defaulted. Affine_role is point or difference. A difference requires zero offset. A physical count requires zero dimensions, its declared counted kind/domain, scale one and offset zero. Reporting names never select dimensions, kinds, scales or roles. A correctly named but dishonestly defined measure cannot be detected from its label by the checker; the migration supplies reviewed definitions from the explicit base exponents, model and derivation, and preserves their provenance.

A parameter has name, description, value, role and uncertainty. Role is quantity, count or metadata. Quantity and count alternatives additionally require descriptor and nonzero, where nonzero is an explicit assumption, never inferred from an expression's name. A value contradicting that assumption is refused. Metadata instead requires metadata and forbids descriptor/nonzero: metadata is either category with a nonempty unique list of permitted value strings, or integer_range with minimum and optional maximum. Matrix orders use integer_range with minimum 1; switches use categories 0 and 1; precision_bits uses categories 24 and 53. Source numeric strings are preserved even when parsed exactly for admission. Missing uncertainty is an error; the none alternative retains the existing explicit absence of declared input uncertainty without claiming certified physical exactness.

The uncertainty field is tagged none or components. Components is a nonempty list of records, permitting measurement and computational components to coexist without being conflated. Each record requires name, class, mode, target, descriptor, source and assurance; class is measurement or computational. Mode is radius, standard, relative-radius, relative-standard, variance or covariance. Target names the owning value; other is required exactly for covariance, and reference exactly for a relative mode. A component contains either magnitude or expression. Magnitude records preserve the original field name sigma or half_width and exact string, or use the corresponding explicit variance/covariance/relative magnitude name for new synthetic cases. Expression uses the expression alternative below. Radii, standard uncertainties and variances must be nonnegative; covariance may be signed. None of these mathematical domain checks certifies their probabilistic or deterministic assurance. The schema carries a separate descriptor for each component, and nrz_units::uncertainty derives its expected kind, dimensions, difference role and scale from its named targets. Input companion declarations use that derived coordinate measure; a claimed mismatch of scale, offset, dimensions or kind is refused, rather than corrected by changing a magnitude. Variance uses squared scale; covariance uses the two target scales' product; relative modes use scale one. Offsets are always zero.

An observable has name, description, descriptor, expression, value, value_kind, derivation and second_route. Keep closed_form as a preserved historical/documentary field, explicitly excluded from executable validation; the new expression field is the sole executable contract. This retains the legacy mathematical text for review instead of silently overwriting evidence. Its value_kind remains exact, decimal-12 or decimal-4, with the existing significant-digit rules. Count outputs must additionally have exact integral values in their domain. An observable that itself represents uncertainty has companion with class, mode, target, optional other/reference, source and assurance. Its descriptor is derived and checked by the same uncertainty path; it is not an ordinary ratio or acceleration merely because those have the same dimensions. The diagnostic difference between two uncertainty estimates is a comparison quantity, not automatically a standard uncertainty of the mean.

An expression is exactly one of:

- algebra: kind = algebra and text, parsed by nrz_algebra::parse with fixed documented Limits. Symbols bind to parameters, typed constants, helpers, uncertainty components and other observables. No implicit multiplication, unit suffix, indexing, binder, symbolic exponent or equation punctuation is added to the grammar.
- unsupported: kind = unsupported, text, code, reason, dependencies and scope. Text preserves the unsupported formula, code identifies the particular limitation, reason is nonempty and specific, dependencies explicitly identify any available declared dependencies, and scope lists expression and, when necessary, relationship/descriptor evidence that cannot be obtained. A limitation marker is chosen deliberately in source, never manufactured as a fallback after an algebra check fails. Invalid ordinary declarations still fail. Supported expressions cannot depend on an unsupported value masquerading as an Input. Unknown names or cycles in the declared dependency graph are refused; prose inside an opaque unsupported text is not claimed to have been parsed or resolved.

The sole migrated relative uncertainty output needs an unsupported relationship/descriptor status as well as an unsupported expression status, as explained for Kepler below. Its intended relative-standard descriptor is retained explicitly, but is not called an admitted Descriptor. This is preferable to inventing a nonzero reference or changing the units API. Every other migrated quantity/companion descriptor is intended to be admitted independently of any unsupported formula.

Source assurance and provenance are supplied claims. Existing source strings are copied verbatim; added assurance descriptions restate existing distinctions such as probabilistic standard uncertainty, separately assumed deterministic enclosure, or unverified first-order comparison. For new helper symbols and output declarations, source points to the existing model/derivation field or the explicit angle convention; it does not replace any original citation or source identity. There are no newly invented computational uncertainty magnitudes in the reference data.

The wire tags are `type` for kind records, `operation` for kind rules, `role` for parameters, `kind` for metadata, uncertainty containers, helper symbols and expressions, and `kind` for equations. Constant helpers use `kind = constant`; derived helpers use `kind = derived`. Algebra equations carry `kind = algebra`, `name`, `left`, `right`, `source` and `assurance`; unsupported equations carry `kind = unsupported`, `name`, `expression`, `source` and `assurance`. Optional lists serialize as empty arrays. Optional scalar fields are absent, never null. Magnitudes are single-key objects: `half_width`, `sigma`, `relative_radius`, `relative_standard`, `variance` or `covariance`, matching the mode.

## Checking and evidence · `sec:nrz:problem-data-validation`

**Rule (Problem data checking)** · `rule:nrz:problem-data-checking`

Construct one Registry/Context for each entry and rebuild or revalidate the value admission for each variant. Kind maps to Ratio, Angle, Named, Count or Uncertainty without dimension-based guessing. Dimension::new receives reduced checked Rational exponents. Measure::new receives the explicit reporting string, Scale::Exact and offset. Descriptor::new checks normal quantity/count descriptors; nrz_units::uncertainty constructs relative and absolute companion descriptors with their actual value/reference relationships. CountDomain::new and Descriptor::check_count_literal enforce exact imports. Keep source DTOs for private domain bounds when serializing; no new engine getters or serde dependencies are needed.

Quantity parameters become Declaration::Input with their declared nonzero assumption and Evidence; fixed numerical values remain independent reference coordinates, not evaluated formula proofs. Count inputs undergo literal admission before declaration. Metadata becomes Declaration::Metadata with its declared category/range retained in the schema. Exact constants become Declaration::Constant. Helpers and ordinary algebra observables become Declaration::Derived. Magnitude companions become Declaration::UncertaintyInput, and uncertainty expressions become Declaration::Uncertainty with Companion target identities. Unsupported outputs are not installed as substitute numerical inputs.

Run check_all after declaring all supported symbols, including unused declarations and uncertainty inputs, so forward references work and unused cycles/errors cannot disappear. Run check for direct declaration probes and expression evidence, check_against for every declared output contract, and check_equation for both original equation sides. Check every original operand, including children under zero, cancellation or zero powers. Do not normalize or evaluate original data before checking. The checker handles consistency; it does not establish equality to the expected numerical answer or the domain of sqrt/log/exp. Do not invoke full numerical substitution of the Rump inputs or treat bounded Rational arithmetic as an arbitrary-precision oracle.

Validate in this order: full TOML/JSON syntax; envelope/version; strict record shape and identity; exact numeric syntax/domain; kind/descriptor/measure construction and rule registration; all name/relationship dependencies; original expression and output checks; variants; deterministic serialization. Reject duplicate names across every declaration category, missing scales, missing symbols, unavailable functions, illegal roles and unsupported schema versions. Numeric decoding uses the existing algebra literal machinery and Rational, with a narrow literal/fraction decoder; it must not accept arbitrary algebra where a value string is required. Zero denominators and rational overflow become path-bearing errors rather than approximate conversions.

Errors identify the source path and field, for example parameters.T_left_C.descriptor.measure.offset or observables.period.expression.text, together with parser byte range or the units Diagnostic's operand path, declaration chain, expected descriptor/rule and derived descriptors. Equation sides retain the checker's leading 0/1 path. Dataset revalidation identifies data/datasets/problems.json plus the entry/source and field. Do not reduce every refusal to an unlocated boolean.

Derived problems.json v2 carries the complete migrated source declarations, source order, role and category/domain contracts, component records, unsupported reasons, and deterministic generated validation records. A validation record has declaration name/category, descriptor status, expression/relationship status, checked descriptor where available, used declaration names, output conversion where relevant, and any explicit unsupported scope/reason. Retain original formula text separately from checking evidence. Serialize only validated DTOs/public-accessor evidence; do not use Debug strings as a persistence schema. check_all evidence distinguishes established and propagated companions when present. For an unsupported body whose target and independent descriptor are admitted, relationship status is `declared`: no established or propagated expression witness is claimed. An unavailable relative relationship has status `unsupported`. A partial entry is reported as checked declarations plus N unsupported expressions, never simply fully checked. The entry validation object has `records`, `checked_observables`, `unsupported_observables`, `checked_expressions` and `unsupported_expressions`. Expression totals include helpers, uncertainty expressions and equations. The catalogue exposes observable counts and every unsupported record’s named reason so limitations remain visible.

render must reconstruct and recheck the committed v2 declarations before using them; it must not trust a serialized checked flag. Compare regenerated evidence with the committed evidence and reject a forged or stale status. data and check use the same validation entry point. Existing source ordering, envelope field ordering, sorted object keys, trailing newline, layout/symlink restrictions and managed-output inventory remain intact. No new third-party dependency is needed; docgen adds workspace/path dependencies on nrz-units and nrz-algebra. This is a tooling dependency and adds no engine-to-tool or scalar-to-units edge.

Variants validate every replacement even if a parameter is unused by the base formulas: exact quantity syntax and any explicit nonzero assumption; integral count membership; permitted metadata category/range. A rejected replacement reports variants.<name>.overrides.<parameter>. A category selecting a different topology or uncertainty scenario does not cause docgen to execute or certify its documentary expected text. The schema declares the observable expressions as base-instance formulas; variant checking proves replacement admission and unchanged declaration contracts, not that the base formula is the new topology's solver. Batch/plan admission notices therefore remain.

After the switch-over, v1 inputs and v1 committed problem datasets are refused. The diagnostic names req:vision:unit-data-migration, the new schema document and the need to supply v2 declarations or an explicit unsupported marker. It never reports a legacy formula as checked. The implementation sequence uses a temporary v1 route in the second commit, explicitly labeled legacy shape validation, to keep the existing files accepted until the atomic third-commit migration. That route is removed in the final commit; there is no long-term legacy compatibility promise.

Current surface limits remain explicit: rational scales only; no shaped matrix/spectral declarations, binders, symbolic exponents or metadata arithmetic; conservative count-domain closure; explicit ordered semantic rules; no arbitrary affine weighted-sum constructor; relative references need a named nonzero difference; a derived declaration supplies no nonzero evidence; companion identity cannot be inferred from equal dimensions; a relative uncertainty cannot be rebound from G to period merely because both relative dimensions are zero. No units/algebra API or behavior addition is proposed.

**Rule (Explicit unsupported evidence)** · `rule:nrz:problem-data-unsupported`

An unsupported expression's `scope` is a unique list containing `expression` and optionally `relationship` and `descriptor`. Descriptor scope requires relationship scope and an uncertainty companion; it retains an intended descriptor and never installs a pretend checked declaration. Dependencies participate in cycle and name checks even though the opaque text is not parsed. Supported expressions cannot consume unsupported declarations. Each reason identifies the missing capability or derivation that would permit a later check. An invalid algebra expression always fails; failure never changes its tag to unsupported.

Fixed parser/checker limits are maximum depth 128, nodes 10,000 and work 100,000. Exact coordinates use the same bounded rational literal grammar, with an optional single fraction of literals. Arithmetic formulas are not coordinate syntax. Overflow and a zero denominator fail without conversion to floating point. A units check does not evaluate the expected numerical result, prove an equation, certify a probability model, infer missing correlations or evaluate variant topology changes.

## Acceptance · `sec:nrz:problem-data-acceptance`

**Requirement (Problem data evidence)** · `req:nrz:problem-data-evidence`

Positive and negative tests pair quantities, counts, ratios and metadata; count domains and variant categories; affine points and differences; exact scales and origins; symbol binding and forward references; kind rules and rational exponent policies; uncertainty scale products and relationship targets; and deliberate unsupported expressions. Refusals include unknown and missing fields, missing scales and symbols, wrong dimensions or kinds, invalid children under cancellation or zero, symbolic exponents, cyclic references, stale generated evidence, and legacy inputs after migration. No test claims that dimensional agreement proves a numerical answer.

The transition has three commits: specify this contract; add v2 checking with an explicitly unchecked v1 shape route and independent synthetic tests; then migrate every input and consumer, remove the v1 route and regenerate the dataset and catalogue together. Mixed-major source trees fail during transition. Every commit reaches the documentation fixed point on its own inputs. After migration, original values, magnitudes, identities, sources, citations and provenance have exact projection equality with the v1 seed; `closed_form` remains documentary evidence.

Shape axes, shared source identities and batch axes remain governed by (`def:nrz:companion-shape`), (`def:nrz:batch-axis`) and their existing implementation notices. This version makes no claim to implement those contracts.
